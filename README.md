# Plumo

Plumo — ИИ-ассистент для входящих обращений бизнеса. Он отвечает по утверждённым данным компании, выясняет потребность, собирает пожелания на встречу или просмотр и передаёт менеджеру запрос с историей и резюме. Переговоры и закрытие сделки остаются человеку.

Продукт ориентирован на русский и кыргызский, включая смешанную речь. Качество кыргызского нужно проверять отдельно с носителем перед пилотом. Недвижимость используется в демо; профиль бизнеса и база знаний позволяют настраивать ядро под другие отрасли.

**Приоритет с 24 октября 2026:** MVP на мессенджерах — WhatsApp, Telegram и Instagram с кабинетом менеджера (раздел [MVP](#mvp)). Телефония отложена.

**Статус на 24 октября 2026:** кабинет `/dashboard` подключён к backend: закрытый вход команды, «Интеграции» и «Диалоги» на данных PostgreSQL, приём Telegram и Instagram через webhook, worker с надёжной очередью и отправкой ответов. Telegram проверен вживую на тестовом боте (приём, ответы модели, передача менеджеру и обратно) на временном публичном адресе. Instagram проверен только тестами на подписанных fixtures: у команды пока нет Meta app и доступов. WhatsApp не подключён, в кабинете — демо-мастер. Лендинг и демо-мастер работают на вымышленных данных. Подробно: [docs/dashboard-channels.md](docs/dashboard-channels.md).

Исходный бюджет — $1000; подтверждённого бюджета на зарплаты нет. Правила работы над проектом — [AGENTS.md](AGENTS.md).

## Как устроен backend

Backend — модульный монолит с одной PostgreSQL. Зависимости собираются в `backend/src/app/container.py`; внешние провайдеры находятся за интерфейсами из `domain/ports.py`.

```text
Нормализованное сообщение / mock-событие канала
  → определение бизнеса и клиента
  → сохранение сообщения и проверка повтора
  → история, резюме и релевантные знания бизнеса
  → роутер → провайдер модели
  → проверка ответа → разрешённые действия / передача человеку
  → обновление памяти, журналы и метрики
  → ответ API для адаптера канала

ElevenLabs Agents
  → initiation webhook: начало звонка и приветствие
  → Custom LLM: реплика → общее ядро агента → ответ в SSE
  → post-call webhook: результат и метрики звонка
```

Telegram и Instagram приходят на `/api/v1/webhooks/*`. Событие и задание сохраняются до ответа провайдеру. Worker (`python -m app.worker`) прогоняет событие через то же ядро и отправляет ответ, заново проверяя режим диалога перед отправкой. Сервисный вход для других адаптеров — `POST /api/v1/messages`. API также предоставляет карточки и историю клиентов, диалоги, очередь передачи менеджеру, базу знаний, встречи и метрики. Контракт — [backend/docs/openapi.json](backend/docs/openapi.json); подключение frontend и каналов — [backend/FULLSTACK.md](backend/FULLSTACK.md).

В БД уже описаны `businesses`, `knowledge_items`, `customers`, `customer_channels`, `conversations`, `messages`, `customer_summaries`, `handoff_requests`, `meetings`, `interaction_logs`, `ai_usage_logs` и `voice_calls`. Миграция `006` добавила операторов и сессии, подключения каналов, входящие события, очередь заданий, исходящие отправки, режим диалога и курсоры прочтения. Всего миграций шесть.

Очередь заданий — таблица PostgreSQL с `SKIP LOCKED`, lease и ограниченными повторами; Redis не нужен. Уведомления менеджеру по-прежнему запускаются фоновыми задачами процесса.

## Данные и ограничения

- Факты о ценах, наличии, сроках и условиях должны приходить из утверждённых данных бизнеса. В ядре есть получение знаний и проверка ответа; надёжность этих ограничений нужно оценивать на сценариях пилота.
- Модель предлагает ограниченные действия, а сервер исполняет их. Произвольного SQL от модели нет.
- Встреча сохраняется со статусом `proposed`: это пожелание клиента, а не подтверждённое резервирование календаря.
- Карточки клиентов, диалоги, подключения и отправки привязаны к `business_id`. Маршруты кабинета берут бизнес из сессии оператора и отвечают 404 на объекты другого бизнеса. Сервисный `PLUMO_API_KEY` знает только сервер Next.js.
- Телефон, написанный в тексте, сохраняется как контакт для обратного звонка и не объединяет карточки. Проверка владения номером для объединения ещё не реализована. Связь WhatsApp и звонка по номеру зависит от доверенного транспорта и корректного caller ID.
- История сообщений и резюме хранятся отдельно от знаний бизнеса. Контекст модели собирается из профиля бизнеса, релевантных знаний, карточки, резюме и ограниченной истории.
- Входящие события дедуплицируются по подключению и id провайдера. Каждая отправка имеет статус `queued/sending/sent/failed/unknown/cancelled`. `sent` значит, что провайдер принял сообщение, а не что клиент его прочитал. Неоднозначный результат остаётся `unknown` до решения человека.
- «Взять диалог» переводит его в режим менеджера и отменяет неотправленные ответы агента. Отправка агента начинается только при совпадении версии режима. Сообщение, уже переданное провайдеру, отменить нельзя. `MANAGER_PAUSE_HOURS` по умолчанию 24; для стенда — `0`, агент не возвращается сам.
- Уведомление менеджеру, просьба перезвонить и перевод активного звонка — разные действия. Работающий перевод активного звонка не подтверждён.
- API-ключи и персональные данные не помещаются в Git. Для конфигурации используются `.env.example`; требования к согласию, записи, хранению и удалению данных необходимо уточнить до работы с реальными покупателями.

## Локальный запуск

Frontend и backend запускаются отдельно. Для просмотра сайта PostgreSQL и API не требуются.

### Frontend

Из корня репозитория, при установленном Node.js согласно [frontend/README.md](frontend/README.md):

```powershell
cd frontend
npm install
npm run dev
```

Сайт: http://localhost:3000. Проверка TypeScript — `npm run typecheck`, сборка — `npm run build`. Кабинету нужны запущенный API и `frontend/.env.local` с `PLUMO_API_URL` и `PLUMO_API_KEY` (образец — `frontend/.env.example`). Без входа `/dashboard` ведёт на `/login`.

### Backend на Windows

Нужен Python 3.12+. Команды ниже выполняются из папки `backend`, а не из корня репозитория:

```powershell
cd backend
.\dev.cmd setup
.\dev.cmd up
```

`setup` создаёт виртуальное окружение, устанавливает зависимости и копирует `.env.example` в `.env`, если файла ещё нет. `up` запускает локальный PostgreSQL через `scripts/local-db.ps1`, применяет миграции, загружает демо-данные и запускает API. Локальный скрипт базы скачивает PostgreSQL при первом запуске.

Swagger: http://127.0.0.1:8000/docs. Проверка здоровья: http://127.0.0.1:8000/health.

Для кабинета и каналов нужны ещё два шага: оператор для входа (`.\dev.cmd operator create --email ... --business "Demo Realty"`) и worker в отдельном окне (`.\dev.cmd worker`). `dev.cmd up` worker не запускает. Подключение бота, публичный HTTPS и Meta описаны в [docs/dashboard-channels.md](docs/dashboard-channels.md).

По умолчанию образец конфигурации использует `AI_MODE=mock`; для этого режима ключ модели не нужен. Seed создаёт вымышленный бизнес Demo Realty и примеры объектов. Интерактивный чат с backend:

```powershell
.\dev.cmd demo
```

### Backend на Linux и macOS

Нужны Python 3.12+ и Docker с Compose v2: PostgreSQL запускается сервисом `db` из `docker-compose.yml`, строка подключения та же, что в `.env.example`. Команды те же, что у `dev.cmd`:

```bash
cd backend
./dev.sh setup
./dev.sh up
```

Оператор и worker — `./dev.sh operator create --email ... --business "Demo Realty"` и `./dev.sh worker` в отдельном терминале. Тесты и линтер — `./dev.sh test`, `./dev.sh lint`.

Папки `.venv`, `.tools`, `.pgdata` и `frontend/node_modules` зависят от ОС: не переносите их между Windows и Linux, а пересоздайте (`setup`, `npm ci`).

### Backend с Docker

Из папки `backend`, с установленным Docker и подготовленным `.env` по образцу `.env.example`:

```powershell
docker compose up -d --build
docker compose run --rm api python -m app.seed
```

Compose поднимает PostgreSQL, API и worker; миграции применяются при старте API. Другие варианты запуска и подключение БД описаны в [backend/FULLSTACK.md](backend/FULLSTACK.md).

Для внешних интеграций нужны собственные ключи и настройки в локальном окружении. При заданном `PLUMO_API_KEY` основной API требует `X-API-Key`; у ElevenLabs отдельная авторизация. Инструкции: [backend/INTEGRATION.md](backend/INTEGRATION.md) и [backend/VOICE.md](backend/VOICE.md). Актуальные API, модели, тарифы и доступность номеров нужно проверить перед подключением; сведения в проектных документах не являются гарантией доступности провайдера.

## Проверки

Frontend, из `frontend`; для прямого запуска тестов с импортом TypeScript нужен Node.js 22.18+ согласно frontend-документации:

```powershell
npm run typecheck
npm run build
node --test tests/*.test.mjs
```

Backend, из `backend` после `setup`:

```powershell
.\.venv\Scripts\python.exe -m pytest tests/unit
.\dev.cmd test
.\dev.cmd lint
```

Unit-тесты не требуют БД. Полный набор требует PostgreSQL; integration-тесты используют отдельную тестовую БД и пересоздают таблицы. Не направляйте их на БД с рабочими данными.

В репозитории есть проверки повторов и конкурентной обработки, изоляции бизнесов, передачи человеку, сбоев моделей, API и голосовых сценариев. Это перечень проверок в коде, а не отчёт об их текущем прохождении.

Живые проверки моделей и голоса, сравнение сценариев и импорт знаний описаны в backend-документации: [BENCH.md](backend/docs/BENCH.md), многошаговые диалоги через всё ядро — [DIALOG_EVAL.md](backend/docs/DIALOG_EVAL.md), [MODELS.md](backend/docs/MODELS.md), [VOICE.md](backend/VOICE.md). Такие проверки могут расходовать средства внешних сервисов. Для голоса оцениваем задержку, перебивания и точность телефонов, адресов, сумм и дат; кыргызский проверяем с носителем.

## MVP

Решение от 24 октября 2026: первая версия — мессенджеры. Клиент пишет в WhatsApp, Telegram или Instagram Direct → агент отвечает по данным бизнеса → при необходимости передаёт диалог → менеджер получает уведомление в Telegram, забирает диалог в кабинете, отвечает в тот же канал и возвращает агенту.

MVP готов, когда:

- все три канала подключаются через кабинет и проходят этот путь вживую на тестовых аккаунтах;
- стенд работает на постоянном домене с HTTPS, worker перезапускается сам, база резервируется;
- уведомление менеджеру не теряется и не дублируется при сбое или повторе;
- один реальный бизнес прошёл согласованный сценарий на своём канале.

Порядок работ:

1. **Надёжность ядра.** Уведомление менеджеру — задание в очереди, создаётся в одной транзакции с передачей. Вызов модели — вне открытой транзакции БД. Сделано: worker в `docker-compose.yml`.
2. **Постоянный стенд.** VPS, домен, HTTPS, резервное копирование, мониторинг worker. Telegram переносится с временного туннеля.
3. **Meta.** Сразу завести Meta app и верификацию бизнеса: она нужна и Instagram, и WhatsApp и занимает дни. Не откладывать до конца разработки.
4. **Instagram.** Живая проверка входящего Direct и ответа (ТЗ §7.4).
5. **WhatsApp Cloud API.** Webhook с проверкой подписи, телефон как ключ клиента, окно ответа и шаблоны вне окна, подключение из мастера кабинета. Условия, цены для KG и способ подключения номера сверить с официальной документацией Meta перед реализацией.
6. **Пилот.** Выбрать бизнес, канал и сценарий; проверить кыргызский с носителем; согласовать хранение и удаление данных; двухнедельный пилот.

Метрики пилота: обращения, корректно обработанные запросы, заявки, подтверждённые встречи и передачи человеку; для команды — стоимость диалога, задержки, ошибки ключевых сущностей и интеграций, результаты отдельно по языкам. До запуска нужно определить знаменатель «самостоятельно обработанного обращения»; корректная передача человеку учитывается отдельно.

Не входит в MVP: телефония, самостоятельная регистрация, роли операторов, платежи, холодный автообзвон, календарь и CRM, объединение карточек между каналами, автоматическое расширение пилота на все каналы. Встречи остаются пожеланием клиента до подтверждения менеджером.

Отложенная телефонная гипотеза — переадресация звонка в Plumo при неответе менеджера — описана в [backend/VOICE.md](backend/VOICE.md). Код голоса сохраняется; возвращаемся к нему отдельным решением.

ТЗ на Telegram и Instagram с критериями приёмки: [docs/dashboard-channel-integration-spec.md](docs/dashboard-channel-integration-spec.md).

Текущий рабочий план — стенд оценки диалогов, доработка Telegram и выбор моделей: [docs/plan-telegram-core.md](docs/plan-telegram-core.md).
