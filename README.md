# Plumo

Plumo — ИИ-ассистент для входящих обращений бизнеса. Он отвечает по утверждённым данным компании, выясняет потребность, собирает пожелания на встречу или просмотр и передаёт менеджеру запрос с историей и резюме. Переговоры и закрытие сделки остаются человеку.

Продукт ориентирован на русский и кыргызский, включая смешанную речь. Качество кыргызского нужно проверять отдельно с носителем перед пилотом. Недвижимость используется в демо; профиль бизнеса и база знаний позволяют настраивать ядро под другие отрасли.

**Статус на 12 октября 2026:** в репозитории есть демонстрационный frontend и отдельный backend с ядром агента, PostgreSQL, адаптерами моделей и кодом интеграции ElevenLabs. Frontend пока не подключён к backend: кабинет и демо используют локальные вымышленные данные. Наличие адаптера не подтверждает настройку сервиса, работу реального канала или готовность к пилоту.

Исходный бюджет — $1000; подтверждённого бюджета на зарплаты нет. Правила работы над проектом — [AGENTS.md](AGENTS.md).

## Как устроен backend

Backend — модульный монолит с одной PostgreSQL. Зависимости собираются в `backend/src/app/container.py`; внешние провайдеры находятся за интерфейсами из `domain/ports.py`.

```text
Нормализованное сообщение / mock-событие канала
  → определение бизнеса и клиента
  → сохранение сообщения и проверка повтора
  → история, резюме и релевантные знания бизнеса
  → роутер → провайдер модели
  → проверка ответа → разрешённые действия / передача человеку
  → обновление памяти, журналы и метрики
  → ответ API для адаптера канала

ElevenLabs Agents
  → initiation webhook: начало звонка и приветствие
  → Custom LLM: реплика → общее ядро агента → ответ в SSE
  → post-call webhook: результат и метрики звонка
```

Основной вход — `POST /api/v1/messages`. API также предоставляет карточки и историю клиентов, диалоги, очередь передачи менеджеру, базу знаний, встречи и метрики. Контракт — [backend/docs/openapi.json](backend/docs/openapi.json); подключение frontend и каналов — [backend/FULLSTACK.md](backend/FULLSTACK.md).

В БД уже описаны `businesses`, `knowledge_items`, `customers`, `customer_channels`, `conversations`, `messages`, `customer_summaries`, `handoff_requests`, `meetings`, `interaction_logs`, `ai_usage_logs` и `voice_calls`. Есть пять миграций: начальная схема, звонки, изоляция бизнесов, метрики звонков и профиль бизнеса.

Отдельного worker и надёжной очереди заданий пока нет. Уведомления менеджеру запускаются фоновыми задачами текущего процесса. До реальных webhook требуется обеспечить надёжное сохранение события и задания, порядок обработки и восстановление после перезапуска. Redis не добавлен.

## Данные и ограничения

- Факты о ценах, наличии, сроках и условиях должны приходить из утверждённых данных бизнеса. В ядре есть получение знаний и проверка ответа; надёжность этих ограничений нужно оценивать на сценариях пилота.
- Модель предлагает ограниченные действия, а сервер исполняет их. Произвольного SQL от модели нет.
- Встреча сохраняется со статусом `proposed`: это пожелание клиента, а не подтверждённое резервирование календаря.
- Карточки клиентов и поиск идентификаторов привязаны к `business_id`. Перед подключением кабинета требуется серверная авторизация и проверка доступа к данным бизнеса; общий API-ключ не заменяет права пользователей.
- Телефон, написанный в тексте, сохраняется как контакт для обратного звонка и не объединяет карточки. Проверка владения номером для объединения ещё не реализована. Связь WhatsApp и звонка по номеру зависит от доверенного транспорта и корректного caller ID.
- История сообщений и резюме хранятся отдельно от знаний бизнеса. Контекст модели собирается из профиля бизнеса, релевантных знаний, карточки, резюме и ограниченной истории.
- Есть проверка повторов по идентификатору сообщения. Это не заменяет надёжную обработку и учёт отправки ответа в реальном канале.
- Принятая менеджером передача подавляет ответы агента. Текущая настройка `MANAGER_PAUSE_HOURS` по умолчанию равна 24; значение `0` сохраняет паузу до закрытия передачи менеджером. Политику нужно согласовать перед пилотом.
- Уведомление менеджеру, просьба перезвонить и перевод активного звонка — разные действия. Работающий перевод активного звонка не подтверждён.
- API-ключи и персональные данные не помещаются в Git. Для конфигурации используются `.env.example`; требования к согласию, записи, хранению и удалению данных необходимо уточнить до работы с реальными покупателями.

## Локальный запуск

Frontend и backend запускаются отдельно. Для просмотра сайта PostgreSQL и API не требуются.

### Frontend

Из корня репозитория, при установленном Node.js согласно [frontend/README.md](frontend/README.md):

```powershell
cd frontend
npm install
npm run dev
```

Сайт: http://localhost:3000. Проверка TypeScript — `npm run typecheck`, сборка — `npm run build`.

### Backend на Windows

Нужен Python 3.12+. Команды ниже выполняются из папки `backend`, а не из корня репозитория:

```powershell
cd backend
.\dev.cmd setup
.\dev.cmd up
```

`setup` создаёт виртуальное окружение, устанавливает зависимости и копирует `.env.example` в `.env`, если файла ещё нет. `up` запускает локальный PostgreSQL через `scripts/local-db.ps1`, применяет миграции, загружает демо-данные и запускает API. Локальный скрипт базы скачивает PostgreSQL при первом запуске.

Swagger: http://127.0.0.1:8000/docs. Проверка здоровья: http://127.0.0.1:8000/health.

По умолчанию образец конфигурации использует `AI_MODE=mock`; для этого режима ключ модели не нужен. Seed создаёт вымышленный бизнес Demo Realty и примеры объектов. Интерактивный чат с backend:

```powershell
.\dev.cmd demo
```

### Backend с Docker

Из папки `backend`, с установленным Docker и подготовленным `.env` по образцу `.env.example`:

```powershell
docker compose up -d --build
docker compose run --rm api python -m app.seed
```

Compose поднимает PostgreSQL и API; миграции применяются при старте API. Другие варианты запуска и подключение БД описаны в [backend/FULLSTACK.md](backend/FULLSTACK.md).

Для внешних интеграций нужны собственные ключи и настройки в локальном окружении. При заданном `PLUMO_API_KEY` основной API требует `X-API-Key`; у ElevenLabs отдельная авторизация. Инструкции: [backend/INTEGRATION.md](backend/INTEGRATION.md) и [backend/VOICE.md](backend/VOICE.md). Актуальные API, модели, тарифы и доступность номеров нужно проверить перед подключением; сведения в проектных документах не являются гарантией доступности провайдера.

## Проверки

Frontend, из `frontend`; для прямого запуска тестов с импортом TypeScript нужен Node.js 22.18+ согласно frontend-документации:

```powershell
npm run typecheck
npm run build
node --test tests/create-agent.test.mjs tests/dashboard-dialogues.test.mjs tests/dashboard-integrations.test.mjs tests/whatsapp-setup.test.mjs
```

Backend, из `backend` после `setup`:

```powershell
.\.venv\Scripts\python.exe -m pytest tests/unit
.\dev.cmd test
.\dev.cmd lint
```

Unit-тесты не требуют БД. Полный набор требует PostgreSQL; integration-тесты используют отдельную тестовую БД и пересоздают таблицы. Не направляйте их на БД с рабочими данными.

В репозитории есть проверки повторов и конкурентной обработки, изоляции бизнесов, передачи человеку, сбоев моделей, API и голосовых сценариев. Это перечень проверок в коде, а не отчёт об их текущем прохождении.

Живые проверки моделей и голоса, сравнение сценариев и импорт знаний описаны в backend-документации: [BENCH.md](backend/docs/BENCH.md), [MODELS.md](backend/docs/MODELS.md), [VOICE.md](backend/VOICE.md). Такие проверки могут расходовать средства внешних сервисов. Для голоса оцениваем задержку, перебивания и точность телефонов, адресов, сумм и дат; кыргызский проверяем с носителем.

## Первый пилот и следующие шаги

ТЗ для подключения Telegram и Instagram к рабочему кабинету, с Git workflow и критериями приёмки: [docs/dashboard-channel-integration-spec.md](docs/dashboard-channel-integration-spec.md).

План — вручную подключить 2–3 бизнеса, по одному согласованному каналу и сценарию на бизнес, затем провести двухнедельный пилот. Конкретные клиенты, вертикаль и критерии результата требуют согласования.

Приоритетная телефонная гипотеза: при неответе, занятости или вне рабочего времени покупатель переадресуется с номера бизнеса в Plumo. Агент выясняет потребность, отвечает по знаниям, собирает желаемое время и передаёт заявку менеджеру. Условия переадресации, доступность номера, caller ID и поведение при недоступности менеджера нужно проверить до запуска.

Ближайшие задачи:

- [ ] Соединить frontend с backend: тестовый чат, сохранение настроек и получение заявок на пилот.
- [ ] Определить доступ к кабинету и реализовать серверную авторизацию с изоляцией бизнесов.
- [ ] Выбрать пилотный бизнес, один канал и сценарий; уточнить состав команды и бюджет.
- [ ] Проверить голосовую цепочку на реальном номере, русском, кыргызском и смешанной речи.
- [ ] Подключить выбранный канал и надёжную обработку событий, повторы и отправку ответов.
- [ ] Проверить передачу человеку, остановку ответов и поведение при сбоях и недоступности менеджера.
- [ ] Определить источник расписания; до его подключения собирать только пожелания на встречу.
- [ ] Согласовать правила данных, резервное копирование и восстановление.
- [ ] Пройти сценарии с бизнесом, провести пилот и оценить качество, стоимость и задержки.

Метрики пилота: обращения, корректно обработанные запросы, заявки, подтверждённые встречи и передачи человеку; для команды — стоимость диалога и минуты, задержки, ошибки ключевых сущностей и интеграций, результаты отдельно по языкам. До запуска нужно определить условия и знаменатель «самостоятельно обработанного обращения»; корректная передача человеку учитывается отдельно.

Межканальную память проверяем отдельным сценарием. Самостоятельная регистрация и подключение, платежи, холодный автообзвон и расширение каждого пилота на все каналы не входят в текущий MVP. Кабинет сейчас служит демонстрацией, а не готовым сервисом управления бизнесом.
