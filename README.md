# Plumo

Plumo — ИИ-ассистент для входящих обращений бизнеса на русском и кыргызском. Он отвечает по данным бизнеса, выясняет потребность, помогает организовать встречу или просмотр и передаёт диалог человеку с историей.

**Статус на 4 октября 2026:** создан Next.js лендинг с анимированным хедером, секциями продукта, примером статистики, FAQ, формой подготовки письма и интерфейсами авторизации. RU/EN реализованы, кыргызский предусмотрен без перевода. Демо сценарное; API модели, backend-авторизация и сохранение заявок ещё не подключены. Начальный бюджет — $1000; расходы на работу команды отдельно не определены.

Правила для разработчиков и кодовых агентов: [AGENTS.md](AGENTS.md).

## Текущий этап: сайт для демонстрации

На главную добавлен адаптивный футер с контактами компании и SVG социальных сетей. Для активных социальных ссылок нужны официальные URL; инструкция в frontend/README.md.

После hero расположен блок «ИИ-агент работает, пока вас нет» с тремя макетами чатов WhatsApp, Telegram и Instagram. Оригинальные узоры фонов сохранены локально. Сценарная анимация показывает набор вопроса, отправку и ответ; каждый чат автоматически повторяет сценарий после четырёхсекундной паузы. Поддерживает RU/EN. Фирменный синий — #2B55FF. Каналы и реальная обработка обращений в этом блоке не подключены.

После мессенджеров расположена секция «От разговора — к следующему шагу»: WhatsApp-переписка и заявка для менеджера с полной историей разговора. Якорь demo ведёт к этой секции. Блок «Каждый разговор. Больше конкретики» удалён с лендинга. CRM и сохранение данных не подключены.

Блок «Как работает» оформлен как интерактивный пайплайн: знакомство, база знаний, проверка и запуск пилота. Этапы переключаются кнопками, показывают описание и соответствующий макет настройки; поддерживаются RU/EN и reduced motion.

Статистика использует Area Chart из Bklit UI: переключение 7/30 дней, выбор показателя, подсказки по дням и доступный с клавиатуры выбор даты. Итоги и доля заявок рассчитываются из одного набора вымышленных данных. Компоненты библиотеки и MIT-лицензия сохранены в frontend/src/components/charts; прокрутка страницы на сенсорных экранах сохранена.

Перед FAQ добавлены тарифы: «Старт» — 5 900 сом/месяц, «Бизнес» — 12 900 сом/месяц (скоро), индивидуальный — по запросу. Бесплатное демо вынесено отдельно. Выбор тарифа передаётся в форму и черновик письма; оплаты и автоматического подключения нет. Цены — исходное предложение для обсуждения пилота.

Пользователь выбрал backend на FastAPI; frontend планируется на Next.js + TypeScript с Tailwind CSS и компонентами shadcn/ui. Ближайшая цель — красивый адаптивный лендинг, демо-чат на вымышленных данных и форма заявки на пилот. PostgreSQL предназначен для хранения; Redis пока не нужен. ## Продукт и границы

Платящий клиент — бизнес. Покупатель — человек, который пишет или звонит этому бизнесу. По документу PM первая гипотеза связана с недвижимостью, но вертикаль и пилотный клиент ещё требуют подтверждения.

Plumo не ведёт переговоры о цене и не закрывает сделку. Он не должен придумывать цены, наличие, сроки или условия. Неизвестный вопрос передаётся менеджеру. CRM бизнеса остаётся внешней системой; необходимость первой интеграции пока не определена.

Полное видение продукта — единая история покупателя между WhatsApp, Instagram, Telegram и звонками. Это направление развития, а не обязательный набор каналов первого пилота.

## Первый пилот

Предложение PM: 2–3 бизнеса, ручное подключение, двухнедельный пилот, один канал и один сценарий для каждого бизнеса.

Приоритетный сценарий для проверки:

1. Покупатель звонит на номер бизнеса.
2. При неответе, занятости или вне рабочего времени звонок переадресуется в Plumo — точное условие согласовывается с бизнесом.
3. Ассистент отвечает по утверждённой базе знаний и выясняет потребность.
4. Собирает желаемое время встречи. Подтверждает запись только при наличии проверенного расписания и успешного резервирования.
5. Передаёт менеджеру заявку и краткую историю.

Уведомление в Telegram не является переводом активного звонка. До реализации определить механизм передачи и поведение, если менеджер недоступен.

## Предлагаемая архитектура

```text
Мессенджер → webhook → сохранение события и задания в PostgreSQL
                                      ↓
                                    worker
                                      ↓
                               Общее ядро агента
                                      ↓
                            отправка и учёт результата

Телефония → потоковая голосовая сессия → распознавание речи
                                      ↓
                               Общее ядро агента
                                      ↓
                          синтез речи → аудио покупателю

Общее ядро:
  инструкции бизнеса + актуальные факты + контекст покупателя
  → API модели → проверка и выполнение разрешённых действий
  → история, результат, расходы, передача человеку
```

Backend и worker предполагаются в одном репозитории. Голосовой контур использует общее ядро, но требует отдельной потоковой обработки, управления паузами и перебиваниями.

| Компонент | Предложение | Статус |
|---|---|---|
| Backend | Python + FastAPI | Выбран; реализация впереди |
| Основная база | PostgreSQL | Предлагается с первой версии |
| Фоновые задачи | Worker и надёжная очередь; для малого пилота возможна очередь в PostgreSQL | Выбрать реализацию |
| Redis | Временное состояние, координация или очередь при необходимости | Не обязателен на старте |
| Текстовая модель | Готовый API за интерфейсом провайдера | Выбрать по тестам |
| Телефония | Провайдер, совместимый с номером и переадресацией бизнеса | Проверить доступность |
| Распознавание и синтез | Готовые сервисы или модели | Сравнить на реальном телефонном аудио |
| Управление пилотом | Ручная конфигурация, уведомления и отчёт | Без личного кабинета |

## Данные и память

Предполагаемые сущности: businesses, channel_connections, customers, customer_identities, conversations, messages, knowledge_items, leads, appointments, jobs, ai_usage.

- Все данные и операции изолируются по бизнесу с первого пилота.
- Карточка клиента содержит контакты, язык, потребность, этап и связи с каналами.
- Полная история хранится отдельно от краткого резюме.
- Контекст модели: инструкции, релевантные факты бизнеса, карточка, резюме и последние сообщения.
- Телефон — атрибут идентификации, но не универсальное доказательство личности. Сохранение caller ID при переадресации нужно проверить.
- В Instagram и Telegram до подтверждения связи могут существовать отдельные карточки. Простого сообщения с чужим номером недостаточно для раскрытия истории.

## Модели и голос: план выбора

Для текстового ядра сравнить OpenAI, Google Gemini и при необходимости Anthropic на одном наборе русских, кыргызских и смешанных диалогов. Конкретные модели, версии, доступность аккаунта и тарифы проверить перед подключением; выбор пока не сделан.

Кандидаты из документа PM для распознавания: ElevenLabs Scribe v2, Google Chirp 3, Kyrgyz Whisper от NineNineSix, Cybernet AI. Для синтеза: ElevenLabs и KaniTTS. Для телефонии: Telnyx и Zadarma. Это список для исследования, а не подтверждение поддержки кыргызского, потокового режима или номеров +996.

Оценивать:

- понимание русского, кыргызского и смешанной речи;
- точность телефонов, адресов, объектов, сумм и дат;
- правильность ответа и действий по данным бизнеса;
- задержку до начала ответа, перебивания и восстановление после ошибок;
- стоимость всего диалога, включая телефонию, распознавание и синтез.

Роутер малой и большой модели предложен PM как способ экономии. Сначала измерить базовый вариант с одной моделью, затем сравнить качество, стоимость и задержку с маршрутизацией. Отсутствие факта в базе не устраняется переключением модели.

## Метрики пилота

Для бизнеса: число обращений, корректно обработанные обращения, заявки и подтверждённые встречи, скорость ответа, передачи человеку.

Для команды: стоимость диалога и минуты звонка, задержки отдельных этапов, ошибки ключевых сущностей, причины передачи, ошибки интеграций, расход моделей и результаты по каждому языку.

До запуска определить знаменатель и условия «самостоятельно обработанного обращения». Правильная передача человеку учитывается отдельно. PM предложил ориентир 60%, но критерий и момент оценки ещё нужно согласовать после полного периода пилота.

## Порядок работ

- [ ] Выбрать пилотный бизнес, сценарий, канал и режим переадресации.
- [ ] Уточнить состав команды и расходы, которые входят в $1000.
- [ ] Проверить телефонию: номер, caller ID, потоковое аудио, перевод звонка и стоимость.
- [ ] Подготовить разрешённые к использованию записи и набор тестовых диалогов.
- [ ] Проверить голосовую цепочку целиком и принять решение о языке первого голосового пилота.
- [ ] Создать backend, миграции PostgreSQL и конфигурацию без секретов в репозитории.
- [ ] Реализовать базу знаний, память, API модели и ограниченные функции действий.
- [ ] Реализовать передачу человеку, остановку ответов и поведение при недоступности менеджера.
- [ ] Добавить расходы, метрики, защиту от дублей, повторы и резервное копирование.
- [ ] Пройти тесты с бизнесом, затем запустить двухнедельный пилот.

Роадмап PM ориентировочно занимает 10 недель: 1–2 — проверки и интервью; 3–5 — MVP; 5–7 — пилоты; 8–10 — обсуждение цены и платное продолжение. Это план, не обязательство по срокам. Оценивать пилоты нужно после их завершения.
