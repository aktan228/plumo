# Самостоятельное подключение Telegram и готовность кабинета

Этапы 6–7: клиент открывает «Интеграции» → Telegram, создаёт своего бота через официальный BotFather, вводит токен и подключает его. Backend проверяет getMe, закрепляет бота только за одним бизнесом и устанавливает подписанный webhook. При конфликте с другой системой требуется отдельная кнопка замены. Ответы агента после подключения выключены.

## Проверка и запуск

На карточке Telegram появляется проверочная ссылка. Клиент открывает её и нажимает Start в Telegram. Подписанный webhook сохраняет событие и задачу до ответа 200. Worker отправляет фиксированное контрольное сообщение без LLM. Оно не создаёт клиента, встречу или рабочий диалог. После подтверждения Telegram статус проверки обновляется и становится доступно включение агента. Для включения также нужна завершённая публикация бизнеса.

Доставка подтверждает принятие сообщения Telegram, а не прочтение человеком. Ссылка действует 15 минут. Неверный код игнорируется. Повтор webhook или повтор Start с тем же кодом не вызывает повторную отправку подтверждения. При неоднозначном таймауте/перезапуске после начала отправки автоматического повтора нет: нужна новая проверочная ссылка. Очередь сохраняет владение попыткой и не позволяет старому worker перезаписать новый результат.

После включения обычные сообщения проходят существующие надёжные очереди приёма/ответов и ядро с данными бизнеса. Отключение выключает агента, отменяет очередь ответов и удаляет зашифрованный токен из подключения. История рабочих разговоров сохраняется. Для повторного подключения или обновления токена его нужно ввести заново.

## Секреты и конфигурация

Миграция 011 добавляет nullable encrypted_token к channel_connections, старые серверные конфигурации остаются совместимыми. Токен приходит только в HTTPS POST, валидируется как SecretStr, не возвращается в API, логи и состояние URL. В браузере он существует только в памяти мастера; после успешного подключения поле очищается и мастер закрывается. В PostgreSQL хранится Fernet ciphertext. Ключ получается из существующего CHANNEL_SECRET_KEY через HMAC-SHA256 с отдельным контекстом бизнес/подключение/версия. Перенос ciphertext в другой бизнес или подключение не позволяет открыть токен.

Сохраняйте CHANNEL_SECRET_KEY стабильным, случайным и достаточно длинным. Его смена потребует повторного ввода токенов и переустановки webhook. PUBLIC_BASE_URL на backend должен быть публичным HTTPS-адресом API Render, PLUMO_API_URL на Vercel — тем же базовым адресом API. Для самостоятельного Telegram файл CHANNEL_CREDENTIALS_FILE не нужен; для прежнего Instagram он остаётся необходимым. Нового обязательного секрета нет.

В Docker включён CHANNEL_WORKER_ENABLED=true: API и worker используют один Runtime, worker стартует и корректно останавливается вместе с приложением. Для небольшого MVP defaults Docker: WORKER_CONCURRENCY=1, WORKER_POLL_INTERVAL_S=1. Если worker запускается отдельно, можно выставить CHANNEL_WORKER_ENABLED=false у API. Запуск через Python сохраняет прежний default false: нужен отдельный python -m app.worker либо явный флаг. Бесплатный хостинг может останавливать весь контейнер при простое; это не круглосуточный SLA.

API: POST /integrations/telegram/connect принимает token или прежний credential_ref; бизнес определяется сессией. POST /integrations/{id}/verification выдаёт новую проверочную ссылку. Существующие check, PATCH agent_enabled и disconnect сохраняются. Чужое подключение даёт 404, занятый бот другого бизнеса — конфликт. Перед публикацией frontend сначала применить alembic upgrade head на backend.

## Готовность кабинета

На экране «Диалоги» отображаются четыре карточки из GET /dashboard/readiness: бизнес опубликован, есть активные знания, выполнен тест текущей опубликованной версии, подтверждён канал. Mock-ответ отмечается как демопроверка; только приветствие по правилу не засчитывается за проверку модели. Новая публикация требует нового теста. У Telegram с клиентским токеном нужна успешная контрольная доставка; у прежних подключений — входящее событие и принятый исходящий ответ. Ошибка/отключение канала снимает готовность. Карточки ведут в мастер, тест и интеграции. Остальные незавершённые разделы остаются soon.

Readiness агрегирует только записи своего business_id, не читает тексты переписки и не принимает бизнес из query/body. Статусы отражают подтверждённые сервером данные и не включают ответы автоматически.

## Проверки и источники

Интеграционные проверки: шифрование и отсутствие токена в ответах, tenant-изоляция, конфликт webhook, контрольное сообщение, дубликаты, неоднозначная доставка, обновление ключа, отключение и настоящее прохождение очереди агентского ответа. Проверяется встроенный worker без ручного drain. Готовность проверяется на двух компаниях, mock/правилах/живом ответе, изменении версии публикации и ошибке канала. Telegram в автоматических проверках заменён контролируемым HTTP-стендом; подключение реального пользовательского бота не заявляется без его токена.

Источники: [Telegram Bot API](https://core.telegram.org/bots/api#setwebhook), [deep linking](https://core.telegram.org/bots/features#deep-linking), [Fernet](https://cryptography.io/en/latest/fernet/).
