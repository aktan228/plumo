# Тест агента в аккаунте

Пункт 5 плана: чат в последнем шаге мастера и в кабинете → «Тестирование» обращается через Next.js к настоящему AgentService. Он использует опубликованные параметры бизнеса, поиск по его знаниям, обычный роутер, настроенный провайдер модели и валидатор фактов. Гостевой просмотр мастера сохраняет прежний локальный сценарный пример; платных анонимных вызовов нет.

## Как проверить

1. Войти, добавить материалы в мастере и заполнить настройки.
2. Нажать «Применить настройки и начать тест». Сначала сохраняется и публикуется текущая версия, затем создаётся тест. Из кабинета можно начать тест уже опубликованных настроек; без публикации есть ссылка в мастер.
3. Написать приветствие, вопрос по FAQ, вопрос без утверждённого ответа и попросить человека. После симуляции передачи ответы останавливаются; продолжение — в новом тесте.
4. Перезагрузить страницу: последние 20 тестов и их переписка восстанавливаются из БД. После новой публикации для проверки новой версии нужно начать новый тест.

AI_MODE=mock и mock-провайдер помечаются в интерфейсе. Живые ответы требуют уже поддержанного сервером провайдера и его ключа на Render. Приветствие и явная просьба о человеке могут обрабатываться правилами без запроса модели. Это не обещание, что каждый ответ использует LLM.

## Отдельное хранение и безопасность действий

Миграция 010 создаёт test_chat_sessions, test_chat_turns, test_chat_budgets. История, краткая память и состояние тестового клиента хранятся в снимке сессии; их нет в customers, conversations, messages, очереди handoff, встречах и рабочих AI-метриках. Данные теста не становятся знаниями бизнеса.

Обычное ядро получает отдельные адаптеры истории, памяти, действий и событий. Действия помечаются как симуляция: не вызываются канал, календарь и провайдер уведомлений. Просьба о человеке останавливает только этот тест. Business ID берётся из проверенной сессии оператора; тело запроса не принимает customer_id, business_id и настройки провайдера. Чужой идентификатор теста даёт 404.

## Повторы, сбои и лимиты

Создание сессии и отправка сообщения используют UUID клиента. Пара (session_id, request_id) уникальна. Повтор принятого запроса возвращает сохранённый результат без нового вызова и расхода; иной текст с тем же ID даёт 409. Неизвестный результат после сетевого сбоя проверяется кнопкой «Проверить отправку» с прежним ID. После подтверждённой ошибки явное «Повторить» создаёт новую попытку. Неудачная попытка не меняет контекст успешного диалога.

Один тест обрабатывает одно сообщение за раз. Маркер pending и резерв бюджета фиксируются до обращения к провайдеру. Зависший после перезапуска процесс восстанавливается как прерванная попытка через 90 секунд, автоматически заново модель не вызывается. Другая вкладка не может одновременно продолжить тот же диалог. Сводка и извлечение контактов выполняются локально; на сообщение разрешено до двух генераций модели и до 25 секунд на ядро. Внутренние повторы HTTP сохраняют настройки существующего провайдера.

Настройки backend (значения по умолчанию):

| Переменная | Значение | Назначение |
| --- | --- | --- |
| TEST_CHAT_DAILY_MESSAGES | 50 | Принятые попытки бизнеса за день |
| TEST_CHAT_SESSION_MESSAGES | 20 | Попытки в одном тесте, включая ошибки |
| TEST_CHAT_DAILY_BUDGET_USD | 1.0 | Порог оценочных расходов и резервов бизнеса |
| TEST_CHAT_TURN_RESERVE_USD | 0.05 | Резерв до вызова модели |

Все тесты бизнеса делят один счётчик в PostgreSQL. Новый тест не сбрасывает дневной лимит; смена дня — по UTC. До 20 новых сессий в день. Успешная попытка заменяет резерв оценкой стоимости всех генераций. При ошибке с неизвестной стоимостью резерв остаётся; частично известная стоимость выше резерва также учитывается. При превышении порога новые попытки отклоняются. Уже выполнявшийся вызов может стоить больше оценки: это порог допуска новых запросов, а не жёсткий лимит счёта внешнего провайдера.

API: GET/POST /api/v1/testing/sessions, GET /api/v1/testing/sessions/{id}, POST /api/v1/testing/sessions/{id}/messages. В браузере — соответствующие /api/plumo/testing/* через белый список BFF. Оба уровня проверяют сессию; запись требует origin и служебный маркер Next.js. Сырые ошибки провайдера, ключи и внутренний снимок клиента не возвращаются. Сначала обновляется backend с alembic upgrade head, затем frontend. Новых обязательных переменных нет.

## Проверка

Интеграционные тесты используют локальный PostgreSQL и управляемый провайдер: опубликованный FAQ и настройки, контекст предыдущих реплик, две компании, отсутствие рабочих побочных действий, конкурентный повтор, ошибка провайдера, восстановление pending, общий бюджет, дневной и сессионный лимиты, смена опубликованной версии. Отдельно проверены upgrade/downgrade 010 с сохранением бизнеса, production-сборка Next.js и полный путь через BFF. Доставка каналов и работа платного провайдера с конкретным production-ключом проверяются отдельно.
