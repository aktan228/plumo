# Дорожная карта junior-разработчика: задачи J-00 … J-07

Источник: `PLUMO_TEAM_TZ_MVP.md` (разделы 4–7). Здесь только то, что делает junior, разбито на мелкие шаги. Всё, что делает тимлид, вынесено в блок «Нужно от тимлида».

Как пользоваться:

- Задачи идут по порядку: J-00 → J-01 → J-02 → J-03 → J-04 → J-05 → J-06 (J-07 в конце, приоритет P1). J-05 можно сдвинуть раньше, если тимлиду нужен мониторинг.
- Одна основная задача одновременно. Один небольшой PR на задачу или её законченную часть.
- Для J-01–J-04 сначала план на страницу, и только после согласования код.
- Задача считается готовой только после демонстрации на staging и прохождения проверок, а не по факту наличия кода.
- Команды запуска не выдумываем: берём из `backend/dev.sh`, `frontend/package.json`, CI. Если нужной команды нет, фиксируем это в J-00.

## Правила, которые действуют на каждый PR

- [ ] Изоляция по `business_id`: запросы, задания, контекст модели, уведомления.
- [ ] Повторы событий не создают дублей (идемпотентность).
- [ ] Сбой внешнего сервиса (Telegram, LLM, БД) обработан и проверен тестом.
- [ ] Для бага сначала падающий тест, потом исправление причины.
- [ ] Никаких `any`, `@ts-ignore`, `# noqa`, `eslint-disable`, пропущенных или подогнанных тестов.
- [ ] Новых зависимостей нет без согласования.
- [ ] Секретов, реальных переписок и персональных данных нет в Git, логах и PR.
- [ ] Новые frontend-компоненты на Tailwind с токенами `plumo-*`, иконки Hugeicons через `frontend/src/components/ui/plumo-icon.tsx`.
- [ ] README и документация обновлены, если изменились запуск, поведение или статус.
- [ ] В описании PR: что изменилось в поведении, как проверено, результаты, миграции и настройки, известные ограничения.
- [ ] Миграции, секреты и production не трогаю: это делает тимлид.

## J-02. Уведомления в надёжной очереди (P0)

Зависит от J-01. Модель задания согласовать с тимлидом до миграции. Ориентиры: `handoff_service.py`, `handoff_notifier.py`, `worker.py`, `domain/enums.py` (JobKind), `JobQueue`, `telegram_provider.py`. Учесть: `HandoffNotifier` в worker уже есть; сначала разобраться, что он делает сейчас, и не дублировать.

**Разбор и план**

1. [ ] Проследить путь уведомления сейчас: от создания handoff до отправки (где `asyncio.create_task`, где `HandoffNotifier`).
2. [ ] Описать план: связь задания с handoff, состояния, ключ дедупликации, политика повторов, поведение при смене адресата. Согласовать с тимлидом до миграции.

**Данные**

3. [ ] Миграция: поля уведомления (состояния `queued/sending/sent/failed/unknown/cancelled` или согласованный эквивалент, число попыток, время последней попытки, ключ дедупликации, связь с handoff).
4. [ ] Новый JobKind для отправки уведомления в `domain/enums.py`.

**Логика**

5. [ ] Создавать handoff и задание в одной транзакции. Удалить старый параллельный путь `asyncio.create_task` для уведомления.
6. [ ] Уникальный ключ дедупликации: повтор события не создаёт второе уведомление для той же передачи.
7. [ ] Worker: обработка нового вида задания после commit, с переходами `queued → sending → sent`. `sent` означает принятие Telegram, а не прочтение.
8. [ ] Политика ошибок:
   - временные ошибки и 5xx: повтор с лимитом попыток и задержкой;
   - 429: учитывать `retry_after`;
   - ошибки доступа (бот заблокирован, чат недоступен): `failed`, требуется вмешательство;
   - неоднозначный timeout после начала отправки: `unknown`, без автоповтора.
9. [ ] Перезапуск worker: уведомления в `sending` без результата переводятся в `unknown` и показываются оператору для ручного решения. Использовать существующую политику исходящих, не обещать exactly-once.
10. [ ] Смена или отключение адресата при ожидающем уведомлении: отменить (`cancelled`) или явно ждать, но не слать молча на неподтверждённый или отключённый адрес.
11. [ ] Очередь уведомлений не блокирует ответы клиенту.
12. [ ] Сообщение «менеджер уведомлён» показывается только после подтверждённого результата. Ошибка видна оператору.
13. [ ] Ссылка из уведомления: вход → кабинет → нужный диалог (сохранить целевой путь через вход). Чужой диалог недоступен.
14. [ ] Сохранить проверку режима диалога и его версии перед новой отправкой ответа агента.

**Тесты**

15. [ ] Откат транзакции не отправляет уведомление.
16. [ ] Повтор webhook не создаёт дубль.
17. [ ] Падение до отправки сохраняет задание.
18. [ ] 429 и 5xx завершаются ограниченными повторами.
19. [ ] Неоднозначный timeout не вызывает слепой повтор.
20. [ ] Ссылка открывает нужный диалог; чужой диалог закрыт.
21. [ ] Смена адресата при ожидающем уведомлении ведёт себя по описанию.

**Завершение**
