# DB-04: менеджер и уведомления

## Пользовательский путь

В Integrations появился блок «Уведомления менеджеру». Это служебный бот, отдельный от бота общения с клиентами. Для бизнеса подтверждается один личный Telegram-чат; группы и несколько адресатов не поддерживаются.

1. Оператор своего бизнеса получает одноразовую ссылку.
2. Менеджер открывает её в Telegram и нажимает «Запустить».
3. Кабинет показывает найденное имя/username и идентификатор личного чата.
4. Оператор проверяет адресата и подтверждает его. До подтверждения активный адресат не меняется.

Ссылка действует 10 минут. Код хранится только как SHA-256 хеш; открытая ссылка показывается только при создании и не восстанавливается из БД. При перезагрузке страницы можно создать новую ссылку, соблюдая 30-секундную задержку между созданиями. Старая ссылка перестаёт работать после новой ссылки, обнаружения кандидата, отмены или отключения. Кандидат тоже должен быть подтверждён до истечения срока.

Подлинность Telegram-события проверяется по отдельному секретному заголовку служебного бота до обработки кода. Обрабатываются только личные чаты с совпадающими sender/chat id и отправителем-человеком. Адресат не принимается из формы. Изменения требуют версии настройки; конфликт другой вкладки возвращает 409.

## Настройка сервисов тимлидом

До развёртывания применить миграцию `018_dashboard_manager_compat`. Требуется отдельный служебный бот и переменные backend:

```dotenv
HANDOFF_PROVIDER=telegram
MANAGER_BOT_TOKEN=
MANAGER_BOT_USERNAME=
MANAGER_WEBHOOK_SECRET=
PUBLIC_BASE_URL=
DASHBOARD_URL=
```

- `MANAGER_BOT_USERNAME` — имя без `@`, соответствующее токену.
- `MANAGER_WEBHOOK_SECRET` — случайная строка 32–256 символов из A–Z, a–z, 0–9, `_`, `-`.
- `PUBLIC_BASE_URL` — публичный HTTPS-адрес backend.
- `DASHBOARD_URL` — origin frontend, без `/dashboard` в конце.
- Для совместимости токен можно брать из прежнего `TELEGRAM_BOT_TOKEN`, если `MANAGER_BOT_TOKEN` пуст. Общий `TELEGRAM_MANAGER_CHAT_ID` **больше не используется** ни как адресат runtime, ни как неявный fallback провайдера.

После настройки выполнить из каталога backend:

```powershell
python -m app.setup_manager_bot
```

Команда проверяет имя бота, отказывается перезаписывать чужой webhook и устанавливает `/api/v1/webhooks/manager-telegram` с отдельным secret token. Она изменяет настоящий webhook и должна запускаться тимлидом в целевой среде. При старте приложения webhook автоматически не меняется. В рамках разработки эта команда против настоящего Telegram не выполнялась.

Состояние `configured` отражает наличие настроек и выбранный Telegram-провайдер; фактическая доступность транспорта подтверждается живой привязкой и доставкой. При mock-провайдере история явно обозначает демонстрационную обработку без внешней доставки.

Основание протокола: [Telegram setWebhook](https://core.telegram.org/bots/api#setwebhook), [Deep Linking](https://core.telegram.org/bots/features#deep-linking). Документация проверена 30 октября 2026.

## Надёжность доставки

Существующий `notify_handoff` создаётся в одной транзакции с передачей. Worker проверяет соответствие бизнеса задания и диалога, выбирает подтверждённого адресата из `manager_recipients` и перед сетевым вызовом фиксирует `manager_notifications.state=sending`. Общего адресата для разных бизнесов нет.

Провайдер принимает успех только при положительном ответе Telegram с `message_id`. Ошибка соединения до передачи запроса и 429 допускают повтор очередью. Таймаут чтения, неоднозначный сетевой результат, 5xx отправки или ответ без подтверждения становятся `unknown`.

После аварии незавершённая попытка становится `unknown` при повторном захвате задания. Безопасность поздних результатов обеспечивается номером поколения отправки; результат старой попытки не меняет новую. Неактуальный владелец lease не начинает новую отправку и не закрывает чужое задание. Сетевая отправка не держит транзакцию БД открытой.

Кабинет показывает последние 10 операций своего бизнеса. Возможны:

- Очередь / отправляется / ожидает повтора.
- Telegram принял сообщение — это не подтверждение прочтения.
- Отказ или исчерпание повторов — требуется проверка.
- Неопределённая доставка — проверить чат и вручную подтвердить получение, отметить недоставку либо явно разрешить повтор.

Ручной повтор требует дополнительного подтверждения в интерфейсе и направляет уведомление текущему подтверждённому получателю. Он может создать дубль, если прежнее сообщение фактически дошло. Если адресат не настроен, уведомление остаётся с видимой ошибкой; после привязки его можно повторить явно. Переподключение не пересылает автоматически накопленные старые уведомления.

Смена или отключение адресата влияет на новые отправки. Вызов, уже начатый с прежним адресатом, отозвать нельзя. Перед восстановлением production-копии БД отключить worker/внешнюю доставку, чтобы накопленные задания не ушли повторно.

## Ссылка на диалог

Карточка уведомления содержит `/dashboard?conversation=<UUID>#chats`. При отсутствии сессии Next.js сохраняет этот путь через login; при завершении сессии браузерный клиент также сохраняет query/hash. В режиме диалогов ID проверяется и подробности запрашиваются существующим API с изоляцией бизнеса. Идентификатор в ссылке сам по себе доступа не даёт.

## Выпуск и откат

1. Подготовить резервную копию, применить миграции до 021 до включения новой версии worker и API.
2. Развернуть совместимые frontend/backend. Подтвердить адресата каждого бизнеса отдельно.
3. Настроить служебный webhook командой выше и выполнить живую приёмку двух бизнесов.
4. Проверить настоящий handoff, адресата, ссылку, захват диалога и ответ менеджера.

Миграция main 013 создаёт единую таблицу адресатов; 018 добавляет версию записи, поколение уведомления и таблицу прежних попыток без переноса общего адресата в бизнесы. При откате приложения сначала отключить внешние уведомления/worker. Старый код может снова использовать общий адресат и не распознаёт новые состояния попыток: включать его доставку без отдельной проверки нельзя. Сохранение таблиц 013/018 предпочтительнее потери истории попыток; downgrade удаляет настройки адресатов и результаты доставки и не является безопасным откатом production-данных.

## Проверки

Unit-проверки провайдера различают безопасный повтор и неизвестный исход, требуют подтверждения отправки и исключают неявный общий адресат. Интеграционные проверки на отдельной PostgreSQL покрывают хеширование, подпись, срок, повтор кода, подтверждение, смену/отключение, два бизнеса, очередь, сбой/перезапуск, ручное разрешение и защиту поколений. Frontend-тесты проверяют разрешённые proxy-маршруты и сохранение прямой ссылки через login.

Результаты запусков записаны в `PLUMO_DASHBOARD_PROGRESS.md` рабочей папки задачи. Визуальная и настоящая Telegram-приёмка до публикации остаются обязательными.
