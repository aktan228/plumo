# Почта аккаунта Plumo: подключение и проверка

Самостоятельная регистрация создаёт пользователя, отдельный бизнес и пустой черновик настройки. Доступ в кабинет открывается после подтверждения почты. Подтверждение и восстановление пароля реализованы собственным backend Plumo; Supabase используется как PostgreSQL, Supabase Auth не подключается.

## Что настроить

1. Создать аккаунт в [Resend](https://resend.com/).
2. Добавить свой домен или поддомен отправки в [Domains](https://resend.com/domains) и перенести выданные Resend DNS-записи в панель домена. Дождаться Verified. Инструкция: [официальная документация](https://resend.com/docs/dashboard/domains/introduction).
3. Создать API key в Resend. Ключ добавить только в переменные backend Render, не в Git, браузер или переменные `NEXT_PUBLIC_*`.
4. В Render → backend → Environment добавить:

| Ключ | Значение |
| --- | --- |
| `RESEND_API_KEY` | Ключ из Resend |
| `AUTH_EMAIL_FROM` | Например `Plumo <account@mail.your-domain.com>`, адрес именно на подтверждённом домене отправки |
| `AUTH_PUBLIC_URL` | Реальный адрес FRONTEND, например `https://your-project.vercel.app`, без пути, query и fragment |

`AUTH_PUBLIC_URL` ведёт на сайт Vercel. `PUBLIC_BASE_URL` и `PLUMO_PUBLIC_URL` из прежних интеграций ведут на backend и не заменяют эту настройку.
Для локальной разработки допускается `http://127.0.0.1:3000` только при `APP_ENV=development`; на стенде и production требуется HTTPS.
Для этих аккаунтных писем отключить click tracking в Resend: ссылка должна сохранять fragment с токеном.

5. Задеплоить backend с миграцией `008_account_email` (`alembic upgrade head`; Docker уже выполняет её при старте), затем frontend той же версии. Ранее созданным аккаунтам миграция сохраняет доступ. Новым публичным аккаунтам требуется подтверждение.
6. На Vercel оставить существующие серверные `PLUMO_API_URL` и совпадающий `PLUMO_API_KEY`. Ключ Resend на Vercel не нужен.

Без настроенного Resend регистрация вернёт понятную ошибку и не создаст аккаунт. Если настройки есть, но Resend отклонил письмо, аккаунт остаётся неподтверждённым: исправить отправителя/домен/ключ и повторить письмо через минуту. Доставка в настоящий ящик проверяется отдельно после подключения сервиса.

## Если своего домена пока нет

Для проверки только на своём адресе можно указать `AUTH_EMAIL_FROM=Plumo <onboarding@resend.dev>`.
Resend разрешает так отправлять только на email, на который зарегистрирован аккаунт Resend. Для регистрации других людей нужен свой подтверждённый домен. [Официальное ограничение тестового отправителя](https://resend.com/docs/knowledge-base/403-error-resend-dev-domain).
Это не отправка писем через Supabase: API key и отправитель всё равно настраиваются на backend Render.

## Сценарий проверки после деплоя

1. Зарегистрировать новый тестовый адрес. На экране ожидание письма, вход в кабинет пока недоступен.
2. Открыть письмо, перейти по ссылке и нажать «Подтвердить почту». Откроется мастер и станет доступен кабинет своего бизнеса.
3. Повторно открыть ту же ссылку: показать недействительную ссылку и возможность запросить новую.
4. Выйти, открыть «Забыли пароль?», запросить письмо, задать новый пароль с повторным вводом.
5. Старый пароль и все старые сессии больше не работают; новый пароль позволяет войти.
6. Проверить папку «Спам» и лог отправки Resend, если письмо не пришло. API не подтверждает фактическую доставку во входящие.

## Ограничения этапа

Ссылки одноразовые: подтверждение 24 часа, сброс 30 минут. В БД только хеши; fragment не передаётся в access logs, а GET не расходует ссылку. Повторные запросы ограничены, ответы на запросы писем не раскрывают наличие аккаунта в JSON. Лимиты IP пока в памяти одного процесса, лимиты на получателя — в PostgreSQL. Полноценная постоянная очередь email и общее распределённое ограничение IP пока не реализованы.

Google OAuth пока отсутствует, кнопка скрыта. Сохранение и восстановление мастера подключены: [описание](onboarding-persistence.md).
