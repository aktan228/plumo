# База знаний в Dashboard

Рабочая ветка: `codex/dashboard-fill`, исходная версия `6535a5e`.

## Поведение

`/dashboard#knowledge` открывает отдельный экран материалов. Доступны поиск, просмотр, добавление и редактирование текста, FAQ, TXT/MD, отключение и повторное включение источников. Ссылки, ранее добавленные в мастере, остаются ссылками: содержимое сайтов не загружается. Лимиты прежние: 10 источников, 100 КБ UTF-8 на источник и 200 КБ суммарно.

Материалы используют существующий `onboarding`-черновик и `useWizardStorage`, без второй системы публикации. В редакторе кнопка «Сохранить в черновик» переносит материал в общий черновик; затем он автоматически сохраняется на сервер. Текст в открытом редакторе сохраняется в памяти при переключении разделов dashboard. Обновление или закрытие страницы с несохранённым текстом вызывает штатное предупреждение браузера.

Публикация требует отдельного подтверждения: применяются **все материалы и настройки общего черновика**, включая изменения из мастера. Для первоначальной публикации бизнес и агент должны быть заполнены в мастере. Незавершённый ввод источника в мастере нужно завершить перед публикацией. Сохранение черновика само по себе опубликованные знания не меняет.

Список «Что сейчас доступно агенту» получает активные опубликованные фрагменты через существующий серверный `GET /knowledge`, включая данные, добавленные командой вне мастера. Такие фрагменты доступны для чтения, а редактируются на этой странице только исходные материалы общего черновика. Дата в списке относится к опубликованному фрагменту.

## Совместимость и конфликты

В `WizardSource` добавлено необязательное JSON-поле `enabled` с серверным значением по умолчанию `true`. Миграция БД не требуется. Публикация пропускает отключённые источники, сохраняя их текст в черновике для повторного включения. Мастер сохраняет поле при восстановлении и показывает отключённое состояние. Демо-ответы также не используют отключённый FAQ.

Оба интерфейса используют одну версию черновика и существующие блокировки/CAS. После изменения в одном интерфейсе устаревшая вкладка другого получает 409 при попытке записать отличающиеся данные. При конфликте исходный ввод остаётся в памяти; пользователь может скачать JSON с черновиком и открытым материалом перед загрузкой текущей версии. Автоматического слияния конфликтующих правок нет.

Frontend и backend из этой ветки нужно выпускать совместно: старый backend отвергает неизвестное ему поле `enabled`, а старый frontend не гарантирует сохранение этого поля. Откат на старую версию требует отдельной проверки совместимости JSON-черновиков.

Отключение материала исключает его из опубликованных фрагментов при следующей публикации. Проверка поведения агента со старой историей и устаревшими фактами остаётся задачей J-03 и живой приёмки качества.

## Проверка

Frontend из каталога `frontend`:

```powershell
node --experimental-strip-types --test tests/*.test.mjs
node node_modules/typescript/bin/tsc --noEmit --incremental false
node node_modules/next/dist/bin/next build --webpack
```

Backend из каталога `backend`, с установленными зависимостями и отдельной тестовой PostgreSQL:

```powershell
python -m pytest tests/unit -q
python -m pytest tests/integration/test_onboarding.py tests/integration/test_published_agent.py -q
```

`TEST_DATABASE_URL` должен явно указывать на отдельную одноразовую БД `plumo_test`. Integration-фикстура удаляет и пересоздаёт её таблицы; рабочую БД использовать нельзя.

Новые проверки покрывают отключение/повторную публикацию, сохранение флага через мастер, конфликт старой версии, изоляцию компаний и ограничение браузерного proxy операцией чтения знаний. Результаты запусков и статус визуальной приёмки фиксируются в `PLUMO_DASHBOARD_PROGRESS.md` в рабочей папке задачи.
