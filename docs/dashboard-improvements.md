# DB-10: замечания и повторная проверка

Реализовано 4 ноября 2026. Раздел `/dashboard#improvements`, миграция `015_improvements`. Frontend и API выпускаются вместе после обновления схемы.

## Создание и исходный ответ

У ответа ассистента в живом диалоге и у успешного ответа в Testing есть действие «Добавить замечание»: неверный факт, нет ответа, передача человеку, язык/тон. Клиент передаёт только ссылку на собственное сообщение либо пару test session/request, категорию, описание и UUID операции. API проверяет бизнес источника, роль assistant или успешность тестового ответа, а исходный ответ и его сведения получает сам. Произвольные snapshot/answer/business_id в теле отклоняются.

Сохраняется неизменяемый snapshot: ответ, предшествующий вопрос, модель, известная версия публикации, дата и ссылки на исходный диалог/тест, отпечатки материалов. Новые ответы сохраняют publication_version и source_versions (ID, заголовок, updated_at, SHA-256 фактически использованного текста) при генерации. Изолированный тест переносит эти отпечатки из своего сообщения в результат попытки. Общая версия публикации относится к опубликованным настройкам и материалам мастера; отдельные ручные материалы дополнительно различаются отпечатком.

У старых живых ответов без метаданных publication_version=null: текущая версия не приписывается историческому ответу. Старые тесты сохраняют версию своей сессии; если отпечатки материалов не записаны, остаются только известные ID/заголовки. Ссылки на материал открывают его текущую версию, а не обещают восстановить прежний текст. Snapshot ответа и записанные отпечатки не изменяются при последующих публикациях/изменениях оригинала.

Повтор создания с тем же UUID и параметрами возвращает ту же запись, в том числе при конкурентных запросах. Переиспользование UUID для другого замечания — 409. Форма при неопределённом сетевом результате сохраняет исходный запрос и повторяет его с тем же ID.

## Жизненный цикл

1. **Новое → В работе.** Оператор берёт замечание в работу; исходный снимок остаётся прежним.
2. **В работе → Исправлено.** Оператор редактирует материалы или настройки через существующие страницы и общий механизм публикации. Переход требует описания исправления и текущей опубликованной версии. Если версия исходного ответа известна, новая должна быть больше неё. Для старого ответа с неизвестной версией это ограничение доказать нельзя — неизвестность показана явно; текущая публикация и дальнейший свежий тест обязательны.
3. **Исправлено → Проверено.** Требуются ручная оценка результата и успешная попытка в новой тестовой сессии, созданной после fixed_at. Сессия и попытка принадлежат тому же бизнесу, их версия совпадает с зафиксированным исправлением и текущей публикацией. Старый, чужой, неуспешный или ещё выполняющийся тест не подходит. В API нельзя подставить ответ проверки или признак успешности — они берутся из теста.
4. **Исправлено/Проверено → В работе.** Можно открыть замечание повторно. Текущее исправление/проверка сбрасываются, прежние доказательства сохраняются в истории переходов.

Переходы блокируют запись и проверяют version. Конкурентное/устаревшее изменение возвращает 409. Проверка текущей публикации сериализована блокировкой бизнес-записи. Чужое замечание отвечает 404. Создание и смена статуса не меняют знания, настройки, очередь или поведение агента автоматически.

## Что означает «Проверено»

Это ручная оценка конкретного повторного ответа для записанной публикации. Проверка имеет scope demo/rule/model; демомодель и ответ правила отмечаются в списке и карточке. Общая приёмка качества/языков J-03 не выставляется автоматически; readiness.quality_accepted остаётся false. После новой публикации verification_current=false и UI показывает, что проверка относится к прежней версии.

verification_current сравнивает версию общей публикации. Изменения ручных источников напрямую вне этого механизма сами не увеличивают её; перед приёмкой таких изменений команда должна выпустить новую публикацию и повторить тест. Записанные отпечатки помогают выявить различие материалов, но не заменяют управление версиями вне мастера.

## Интерфейс и данные

Есть фильтр статуса, страницы по 20 записей с курсором, карточка исходного ответа, ссылки на материалы/настройки/Testing, выбор подходящей сессии и успешного ответа для ручной оценки, история со ссылками на прошлые подтверждающие тесты. Прямые ссылки на замечание и тест сохраняются через вход. Данные ограничены бизнесом сессии; source pointers сами по себе доступа не дают.

Черновики заметок для разных замечаний сохраняются отдельно в памяти смонтированной страницы и при переходе к материалам/настройкам. Обновление/закрытие с вводом вызывает предупреждение браузера. Постоянное хранение клиентских текстов в localStorage не добавлялось. При конфликте версия ввода сохраняется; применить текст к актуальной карточке можно явно после просмотра изменений. Нативная визуальная и мобильная приёмка пока не выполнены.

## Выпуск и проверка

Из backend выбранной рабочей копии задайте PYTHONPATH=src и явную DATABASE_URL, затем `python -m alembic upgrade head`. Общий QA Python env может быть привязан к другому editable checkout; экспортировать OpenAPI также нужно с PYTHONPATH=src. На пустой QA-базе проверяются 001→015 и 015→014→015. Downgrade удаляет все замечания и доказательства; для наполненной базы предпочтителен откат приложения с сохранением таблицы.

Автотесты покрывают весь цикл на реальном sandbox, публикацию и свежесть доказательств, чужие источники/замечания/верификацию, неуспешный ответ, конфликты и конкурентные запросы, фильтры/страницы, неизвестную старую версию и неизменность snapshot после публикации. Результаты и ограничения общего релизного прогона — в PLUMO_DASHBOARD_PROGRESS.md рабочей папки задачи.
