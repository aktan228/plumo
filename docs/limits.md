# Лимиты частоты и расходов

Применяются к сообщениям клиентов из каналов (Telegram, Instagram), которые обрабатывает worker. У тестового чата свой бюджет (`TEST_CHAT_*`), он сюда не входит. Сервисный `POST /api/v1/messages` лимитами не ограничен: его знает только сервер Next.js.

## Пределы (`backend/.env`)

| Переменная | По умолчанию | Что ограничивает |
|---|---|---|
| `LIMIT_SENDER_MESSAGES` / `LIMIT_SENDER_WINDOW_S` | 10 / 300 | сообщений от одного клиента одного бота за окно |
| `LIMIT_BUSINESS_DAILY_CALLS` | 300 | ответов агента бизнеса за UTC-сутки |
| `LIMIT_BUSINESS_DAILY_USD` | 3 | расход модели бизнеса за UTC-сутки |
| `LIMIT_SERVICE_DAILY_USD` | 20 | расход всего Plumo за UTC-сутки |
| `LIMIT_QUEUE_PER_BUSINESS` | 200 | ожидающих заданий бизнеса |
| `TURN_RESERVE_USD` | 0.01 | резерв на один ответ (модель, извлечение, резюме) |
| `COST_VERSION` | 2026-10 | версия таблицы цен, пишется в каждый резерв |

## Как работает

1. Перед ответом worker резервирует `TURN_RESERVE_USD` и один вызов в бюджете бизнеса и сервиса в отдельной короткой транзакции и фиксирует её до вызова модели. Проверка и прибавление — один `UPDATE` с пределом в `WHERE`: два worker не займут последнее место вдвоём.
2. После ответа резерв заменяется фактической стоимостью из ответа ядра.
3. Резерв уникален на входящее событие: повтор webhook или задания не списывает второй раз.
4. Если worker упал во время ответа, резерв остаётся в расходе: вызов мог быть оплачен. Автоматически он не возвращается.
5. Предел исчерпан: модель не вызывается, сообщение сохраняется в диалоге, ответ клиенту не уходит. На диалог создаётся одна передача менеджеру с причиной `sender_rate_limit`, `business_budget` или `service_budget`. Повторные сообщения новых уведомлений не создают.
6. Очередь бизнеса полна: событие сохраняется со статусом `failed` и `queue_full`, задание не создаётся.
7. Сутки считаются по UTC; новая дата начинает новый счёт, прошлые строки остаются для истории.

Остаток своего бизнеса: `GET /api/v1/limits` (чужие бюджеты недоступны: бизнес берётся из сессии).

Миграция `015_spend_limits`: `spend_budgets`, `spend_reservations`.

## Проверки

`backend/tests/integration/test_spend_limits.py`: исчерпанный бюджет (сообщения сохранены, одна передача), частый отправитель, конкурентные резервы, повтор события и упавший worker, смена суток, спам одного бизнеса не мешает другому, общий предел сервиса, полная очередь.

Не сделано: вызов модели по-прежнему идёт внутри открытой транзакции обработки сообщения (известное ограничение из README, «Надёжность ядра»). Резерв от этого не зависит: он фиксируется отдельно до вызова.
