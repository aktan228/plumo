# DB-04: решение перед реализацией

- Один подтверждённый личный Telegram-чат на бизнес. Новый получатель не заменяет действующего до подтверждения оператором.
- Одна строка настройки на бизнес: активный адресат, версия, хеш одноразового кода, срок, обнаруженный кандидат. Внешний код появляется только в ответе создания ссылки, не сохраняется открытым и не пишется в логи. Ссылка действует 10 минут.
- Подлинность события служебного бота проверяется отдельным Telegram secret header до чтения кода. Группы, боты, чужой sender/chat и повтор кода не привязывают получателя. После обнаружения кандидат подтверждается в сессии своего бизнеса с проверкой версии.
- Существующая PostgreSQL-очередь уведомлений сохраняется. Telegram-адресат выбирается по business_id задания; общий TELEGRAM_MANAGER_CHAT_ID не используется рабочим runtime.
- Перед сетевой отправкой фиксируется попытка. Неопределённый исход и незавершённая попытка после перезапуска требуют ручного решения, а не слепого повтора. Подтверждённый отказ с возможностью повтора использует существующую очередь.
- В кабинете показываются состояние получателя и последние операции доставки своего бизнеса; ручное решение доступно только своему бизнесу. Ссылки открывают конкретный диалог.
- Новая миграция добавляет настройки получателя и попытки отправки, не переносит общий chat_id в клиентские бизнесы. Доступы служебного бота и его webhook настраивает тимлид отдельной командой; работа над кодом не меняет настоящие webhook.

Проверка: два бизнеса и два адресата, поддельное/просроченное/повторное событие, конфликт версий, отказ/таймаут/перезапуск, ручное решение unknown, миграции пустой тестовой БД и регрессии существующей очереди.

Основание протокола: [Telegram setWebhook](https://core.telegram.org/bots/api#setwebhook) и [Deep Linking](https://core.telegram.org/bots/features#deep-linking), проверены 30 октября 2026.
