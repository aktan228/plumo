# ТЗ: Telegram и Instagram в рабочем кабинете Plumo

Дата: 12 октября 2026. Исполнитель: fullstack-разработчик команды. Статус: задание на реализацию; перечисленные ниже новые возможности ещё не реализованы.

## 1. Цель и ожидаемый результат

Подключить существующий `/dashboard` к FastAPI и добавить реальные текстовые обращения через Telegram-бота и Instagram Direct. После выполнения команда должна пройти весь путь: клиент пишет в канал → Plumo сохраняет обращение → агент отвечает → менеджер видит переписку и контекст в кабинете → забирает диалог → отвечает из кабинета в тот же канал → возвращает диалог агенту.

Сохраняем существующий внешний вид кабинета. Результат — рабочий стенд для команды и проверки пилота, с сохранением в PostgreSQL и ограниченным доступом. Демонстрация с локальными массивами вместо реальных сообщений не считается выполнением задачи.

Прочитай перед началом [README](../README.md), [AGENTS.md](../AGENTS.md), [backend/README.md](../backend/README.md), [FULLSTACK.md](../backend/FULLSTACK.md), [INTEGRATION.md](../backend/INTEGRATION.md) и код затрагиваемых модулей. Документы backend местами содержат устаревшие утверждения: контракт и поведение сверять с кодом, API каналов — с официальной документацией.

## 2. Git workflow: сначала develop, затем feature

Работаем по схеме `main → develop → feature → PR в develop → проверка → PR в main`.

1. Обнови ссылки на удалённые ветки и проверь рабочее дерево. Незакоммиченные изменения сохрани отдельно; не используй `reset --hard` и не удаляй чужую работу.
2. Создай локальную `develop`, отслеживающую `origin/develop`, если локальной ещё нет. Если `develop` нет вообще, создай её от актуальной `origin/main` и опубликуй.
3. Убедись, что `develop` содержит текущий frontend и backend. При необходимости сначала согласуй и проведи PR `main → develop` для синхронизации базы.
4. От актуальной `develop` создай `feature/dashboard-telegram-instagram`.
5. Все изменения по задаче коммить и публикуй в feature-ветку. Открой PR с базой `develop`; после ревью и приёмки изменения попадут в `main` отдельным PR.

На момент подготовки ТЗ локальная `main` и удалённые ссылки показывают: `origin/develop` уже существует, но отстаёт от `main` на 29 коммитов. Это наблюдение по текущим ссылкам, не результат свежего `fetch`. Не создавай новую удалённую ветку поверх существующей и не начинай работу от устаревшей базы.

Обычный вариант, когда `origin/develop` уже есть:

```powershell
git status --short
git fetch origin
git switch --track -c develop origin/develop
git pull --ff-only origin develop
```

Если локальная `develop` уже существует, вместо команды её создания выполни `git switch develop`. Если требуется синхронизация с `main`, сначала проведи указанный выше PR, затем снова обнови `develop`.

После синхронизации базы:

```powershell
git switch -c feature/dashboard-telegram-instagram
# Реализация, проверки и небольшие осмысленные коммиты
git push -u origin feature/dashboard-telegram-instagram
```

Только если `develop` отсутствует и локально, и на сервере:

```powershell
git switch -c develop origin/main
git push -u origin develop
git switch -c feature/dashboard-telegram-instagram
```

Не пушить реализацию напрямую в `main` или `develop`; не использовать force push в общие ветки. Создание первоначальной `develop` — отдельный шаг подготовки workflow. Для обновления feature использовать согласованный в команде merge или rebase, сохраняя чужие коммиты.

## 3. Объём задачи

Обязательно:

- Реальный Telegram-бот для входящих текстовых сообщений в личных чатах.
- Реальный Instagram Direct для одного согласованного профессионального тестового аккаунта.
- Серверное хранение подключений, переписок, статуса передачи и состояния отправки.
- Рабочие разделы «Интеграции» и «Диалоги» на данных backend.
- Ответы агента через существующий `AgentService`; ответ менеджера из кабинета с отправкой в канал.
- Защищённый доступ для команды, изоляция по бизнесу, защита webhook, обработка повторов и сбоев.
- Воспроизводимый запуск, проверки и демонстрация на двух реальных каналах.

Первая версия ограничена текстом и личными обращениями. Фото, документы, voice, видео, реакции и редактирование сообщений обрабатываются безопасно как неподдерживаемые события; их распознавание и полноценный просмотр вложений в это ТЗ не входят. Группы Telegram, личные Telegram-аккаунты, Telegram Business connections, комментарии Instagram, массовые рассылки и импорт старой истории также не входят.

Не подключать WhatsApp и телефонию в рамках этой задачи. Существующий мастер WhatsApp оставить рабочим в его текущем демонстрационном объёме. Не переделывать лендинг, тарифы и дизайн, не добавлять оплату, самостоятельную регистрацию, CRM и резервирование календаря.

На старте достаточно одного подключения каждого канала на бизнес. Ограничение должно проверяться сервером. Несколько бизнесов должны быть изолированы с первого дня; один внешний бот или Instagram-аккаунт нельзя одновременно привязать к разным бизнесам.

## 5. Архитектура и надёжная обработка

Остаёмся в одном репозитории и backend. PostgreSQL — источник истины. Для этого объёма предпочтительны таблицы заданий и простой worker внутри проекта; отдельные микросервисы и Redis без обоснования не вводить.

```text
Telegram / Meta webhook
  → проверка подлинности
  → определение подключения и business_id
  → транзакция: входящее событие + задание
  → HTTP 2xx после commit
  → worker: нормализация → существующий AgentService
  → транзакция: история / действия / исходящее задание
  → отправка адаптером с повторной проверкой режима
  → сохранение результата провайдера

Dashboard → защищённый серверный API → PostgreSQL
Ответ менеджера → исходящее задание → тот же адаптер канала
```

Требования к обработке:

1. Не ждать модель в webhook. Подтверждать приём только после надёжного сохранения события и задания в одной транзакции. При отказе БД вернуть ошибку; принятый запрос не должен бесследно теряться после перезапуска.
2. Уникальность входящего события привязать к подключению и внешнему ID. Для Telegram использовать `update_id`; для Instagram выбрать и документировать ключ для конкретного типа события. Не дедуплицировать разные события по одному лишь тексту.
3. Повтор уже обработанного события не создаёт новое сообщение, действие, задание отправки или новый вызов модели. Повтор во время обработки также не запускает второй обработчик.
4. Сохранять порядок внутри диалога. Два сообщения одного клиента обрабатываются последовательно; разные диалоги могут работать параллельно. Зафиксировать порядок по сохранённой последовательности и учитывать доступные ID/время провайдера; позднее событие не должно переупорядочивать уже отправленные ответы.
5. Worker должен иметь безопасное получение задания, ограниченные повторы, таймауты, lease/восстановление зависших заданий и состояние окончательной ошибки. После рестарта продолжать незавершённую обработку.
6. Ответ агента и его исходящее задание сохранять согласованно. Повтор отправки не должен повторять генерацию, создавать вторую встречу или повторно выполнять бизнес-действие.
7. Перед каждой отправкой заново проверять подключение, `agent_enabled`, режим диалога и версию состояния. Устаревший ответ агента после передачи человеку отменять. Устаревшую команду менеджера после возврата агенту также не отправлять.
8. Ответ провайдера с ID сообщения означает принятие сообщения провайдером, а не доказательство прочтения клиентом. Отображать это различие в статусах.
9. Для 429 учитывать разрешённый провайдером интервал повтора; для временных сбоев использовать ограниченный backoff. Недействительный токен и запрет отправки не повторять бесконечно.
10. Timeout после передачи запроса провайдеру может означать неизвестный результат. Нужен статус `unknown` и процедура сверки/ручного решения; без поддержки идемпотентности провайдером нельзя обещать exactly-once и слепо повторять неоднозначную отправку.

Пример допустимой политики: до 3 повторов временной отправки с backoff, затем `failed`; неоднозначный результат — `unknown`, без автоматического повтора до сверки. Точные интервалы и исключения опиши в инструкции.

Внешний платный вызов модели может успеть выполниться до аварии процесса и commit. Документируй этот предел гарантий: дедупликация сохранённых событий не доказывает отсутствие повторного биллинга при любом падении.

## 6. Telegram: подключение и переписка

### 6.1. Пользовательский путь

1. В «Интеграциях» менеджер выбирает Telegram и видит, что подключается бот бизнеса.
2. Для внутреннего стенда оператор заранее создаёт бота и размещает токен в серверном окружении. В кабинете выбирается доступная этому бизнесу серверная конфигурация; секрет не показывается.
3. Нажатие «Проверить и подключить» вызывает backend: проверка бота, установка webhook, сохранение подключения.
4. Кабинет показывает имя и username бота, состояние webhook, состояние автоматических ответов и кнопку открытия бота.
5. Оператор пишет боту с другого тестового аккаунта и видит обращение в «Диалогах».
6. После проверки отдельно включает ответы агента. Переключатель работает через backend и сохраняется после перезагрузки.

Это ручное подключение тестового бизнеса, а не самостоятельная регистрация клиентов. В инструкции объяснить создание бота через BotFather и настройку серверного credential. Если выбран ввод токена через UI вместо серверной подготовки, предусмотреть защищённую одноразовую отправку и шифрованное серверное хранение; не сохранять токен в browser storage.

### 6.2. Backend

- Проверка конфигурации через `getMe`, регистрация через `setWebhook`, диагностика через `getWebhookInfo`, отключение через `deleteWebhook`.
- Для стенда нужен публичный HTTPS callback. Не запускать `getUpdates` одновременно с webhook для одного бота.
- Перед регистрацией проверить существующий webhook. Если он принадлежит другой системе, показать конфликт и не перезаписывать его молча. При отключении удалять только собственную подтверждённую настройку; не сбрасывать pending updates без явно согласованной необходимости.
- Использовать отдельный `secret_token` и проверять `X-Telegram-Bot-Api-Secret-Token`. ID подключения в URL сам по себе не авторизует webhook.
- Принимать текст из личного чата; стабильно использовать Telegram user/chat ID, а не изменяемый username. Сохранять `chat_id`, чтобы отправлять в исходный чат.
- Обрабатывать `/start` как отдельный согласованный сценарий, например краткое приветствие с раскрытием, что отвечает ИИ. Сервисные события не выдавать за запрос клиента.
- Отправлять через `sendMessage`; контролировать длину ответа и безопасный формат, не допускать ошибок из-за пользовательского Markdown/HTML.
- Неподдерживаемые сообщения помечать без запуска модели по пустому тексту. Не зацикливать служебные автоответы.
- Отзыв токена, блокировка бота, недоступность webhook и ограничения отправки должны иметь понятное отражение в кабинете.

Не использовать один глобальный `TELEGRAM_BOT_TOKEN` как неявный канал всех бизнесов. Текущее уведомление менеджеру и клиентская переписка должны иметь явные раздельные конфигурации. Отключение клиентского канала не должно случайно отключать бот уведомлений.

Официальный источник методов и webhook: [Telegram Bot API](https://core.telegram.org/bots/api). Проверено при подготовке ТЗ; перед реализацией сверить актуальные параметры используемых методов.

## 7. Instagram: подключение и Direct

### 7.1. Сначала проверить доступы

На первом этапе зафиксировать выбранный вариант официального API, поддерживаемый тип аккаунта, необходимые разрешения, режим Meta app и допустимых тестовых пользователей. Предпочтительный путь для исследования — Instagram API with Instagram Login. Не смешивать его токены и permissions с Facebook Login.

Официальная коллекция Meta описывает Instagram Login для профессиональных аккаунтов Business/Creator, разрешения `instagram_business_basic` и `instagram_business_manage_messages`; для этого варианта связанная Facebook Page не требуется. Переписку инициирует клиент. См. [официальную документацию Meta в Postman](https://www.postman.com/meta/workspace/instagram/documentation/23987686-9386f468-7714-490f-9bfc-9442db5c8f00).

Это не подтверждает, что у команды уже есть соответствующие разрешения или доступ к произвольным внешним аккаунтам. Исполнитель должен проверить в своём Meta app: права, подписки, роли тестеров и требования для выхода за тестовый режим. Версию API выбрать по актуальной документации и закрепить в конфигурации.

Для внутреннего стенда допустима ручная подготовка авторизованного токена на сервере и подключение заранее разрешённого тестового аккаунта через кабинет. В UI явно указать этот способ. Полный OAuth для самостоятельного подключения чужих бизнесов не обязателен в этой задаче. Если реализуется OAuth, обязательны серверный обмен кода, одноразовый `state`, проверка привязки к сессии и разрешённый redirect URI.

### 7.2. Пользовательский путь

1. Карточка Instagram объясняет необходимость подходящего профессионального аккаунта и доступов Meta.
2. Менеджер выбирает подготовленную конфигурацию либо проходит реализованный официальный OAuth.
3. Backend проверяет аккаунт и доступ к сообщениям, настраивает подписки выбранного API и сохраняет связь с бизнесом.
4. Кабинет показывает аккаунт, способ подключения, здоровье интеграции, ограничения тестового режима и состояние ответов агента.
5. Тестовый клиент пишет в Direct; входящее сообщение появляется в кабинете и получает ответ в том же Direct после включения агента.

### 7.3. Backend

- Реализовать верификацию callback и проверку подлинности POST webhook по правилам выбранного Meta API. Проверку подписи выполнять на исходном теле запроса; challenge и подпись — разные проверки.
- Выбирать бизнес по подтверждённому внешнему ID получателя и серверной связи с подключением. Не доверять `business_id`, присланному в произвольном payload.
- Хранить scoped ID отправителя вместе с подключением. ID из разных профессиональных аккаунтов не считать общей идентичностью клиента.
- Обработать все события в batch; не терять остальные сообщения из одного webhook.
- Использовать стабильный ID входящего сообщения для дедупликации. Не запускать агента на echo собственных ответов, read/delivery events и служебные события.
- Отправлять текст через официальный Send API выбранного варианта подключения. Сохранять ID и результат отправки, ошибки разрешений и ограничения провайдера.
- Перед отправкой проверять актуальное разрешённое окно ответа. Вне окна блокировать отправку, объяснять причину менеджеру; не применять human-agent исключения к ИИ. Численные сроки и исключения подтвердить по текущим правилам Meta и зафиксировать в инструкции.
- Обработать истечение и отзыв токена: `action_required`, остановка новых отправок, понятная инструкция переподключения. Для ручного токена описать его замену; для OAuth — поддерживаемое обновление и отзыв.
- После отключения не отправлять накопленные ответы автоматически при повторном подключении. Возобновление старых заданий требует явной безопасной политики.

- [Instagram Webhooks](https://developers.facebook.com/docs/instagram-platform/webhooks).
- [Graph API Webhooks: настройка и безопасность](https://developers.facebook.com/docs/graph-api/webhooks/getting-started).

При подготовке ТЗ часть страниц developers.facebook.com возвращала ограничение доступа/429; параметры подписи, сроков и App Review здесь не выдаются за полностью проверенные. Перед кодированием исполнитель обязан сверить их в доступной официальной документации и Meta app.

### 7.4. Что делать, если Meta блокирует живой тест

Ранний результат этапа — список конкретных недостающих доступов и действий владельца аккаунта, с понятными инструкциями. Продолжить Telegram, backend и кабинет; для Instagram сделать контрактные тесты на вымышленных подписанных fixtures и показать `Требуется действие`, а не `Подключён`.

Такой результат можно принять как завершённый промежуточный этап разработки, но полная задача по Instagram остаётся невыполненной до живой проверки входящего Direct и ответа. Отсутствие App Review или тестовых прав не заменять неофициальным API, паролями Instagram или браузерной автоматизацией аккаунта.

## 8. Серверное хранение и состояния

Добавить миграции, не переписывая существующую историю миграций. Названия ниже ориентировочные; итоговую схему описать в PR.

| Сущность | Минимум данных |
|---|---|
| Подключение | `id`, `business_id`, канал, внешний ID аккаунта/бота, название, ссылка на серверный credential, статус, `agent_enabled`, последняя проверка/событие/ошибка, timestamps |
| Входящее событие | Подключение и бизнес, внешний event ID, тип, нормализуемые данные, время получения, состояние обработки; уникальность по подключению и ID |
| Задание | Тип, ссылки на событие/диалог, бизнес, статус, число попыток, срок следующего запуска, lease и последняя обезличенная ошибка |
| Исходящее сообщение/отправка | Бизнес, диалог, подключение, роль автора, текст, idempotency key, версия режима, статус, число попыток, ID провайдера, timestamps |
| Состояние диалога | Связь с подключением, фактический режим, handoff, версия состояния и позиция прочтения для оператора |

В существующих диалогах нет прямой связи с подключением. Добавить её либо описать однозначное альтернативное сопоставление и миграцию. Внешний ID клиента должен быть ограничен подключением: при замене Instagram-аккаунта нельзя случайно открыть прежнюю историю другому человеку. Сохранение старой истории при переподключении того же аккаунта должно быть предсказуемым.

Состояния подключения:

- `not_connected`: активное подключение отсутствует.
- `connecting`: выполняется проверка или настройка.
- `connected`: подтверждены аккаунт, права и настройка приёма; отдельно видны результат живой проверки и состояние агента.
- `action_required`: нужны права, замена токена или действие владельца.
- `error`: технический сбой с понятной причиной и повторной проверкой.
- `disconnected`: отключено пользователем; история сохранена, приём/отправка выполняются по явно определённой политике отключения.

Само сохранение формы не переводит интеграцию в `connected`. Старый успех проверки не скрывает последующую ошибку. Кнопка выключения агента останавливает автоматические ответы, но сохраняет приём сообщений; менеджер может забрать диалог и ответить, если канал разрешает отправку.

Важные ограничения данных:

- Все действия и задания несут `business_id`; backend проверяет принадлежность связей.
- Секреты — в серверном окружении/хранилище; в БД допустима ссылка на credential. При сохранении самого токена в БД требуется шифрование с отдельным ключом вне БД.
- Токены, service keys и webhook secrets не возвращать в GET API, не сохранять в localStorage/sessionStorage и не писать в логи. У Telegram токен находится в URL API: редактировать также URL в HTTP-логах и исключениях.
- Сырые webhook могут содержать персональные данные. Сохранять только необходимое, ограничить доступ и срок хранения; в технических логах использовать ID и обезличенные ошибки.
- Отключение не удаляет историю; удаление данных и перенос аккаунта между бизнесами не выполнять неявно.

## 9. Dashboard и доступ команды

### 9.1. Минимальная авторизация

Реальные сообщения нельзя показывать на текущем публичном `/dashboard`. До подключения каналов реализовать закрытый вход для команды без публичной регистрации: например, заранее созданный оператор и серверная сессия с HttpOnly cookie. Для пилотного стенда достаточно одного оператора с одной разрешённой бизнес-областью; в тестах нужны две разные области для проверки изоляции.

Требования:

- Защитить страницу, серверные API и все действия; скрытие кнопки в браузере не является проверкой доступа.
- Backend получает проверяемую identity и разрешённый бизнес. Переданный пользователем `business_id` или ID объекта проверяется по правам оператора.
- Не отдавать `PLUMO_API_KEY` браузеру и не использовать `NEXT_PUBLIC_*` для секретов. Предпочтительно браузер → Next.js server routes/BFF → FastAPI; допустим прямой API с безопасной пользовательской сессией. BFF не должен быть открытым прокси к произвольному backend endpoint.
- Для cookie-сессии определить срок, logout, защиту изменения состояния от CSRF и безопасные cookie-флаги для HTTPS. Закрыть непредусмотренные CORS origins.
- Существующие API чтения/действий также должны проверять business scope; добавление новых защищённых маршрутов не оправдывает оставшиеся доступные обходные маршруты.
- Настройки доступа команды находятся на сервере, а не в исходниках. Полноценные роли, публичная регистрация и Google OAuth не входят в задачу.

### 9.2. Раздел «Интеграции»

Показывать сохранённые backend-состояния Telegram и Instagram, аккаунт, состояние ответов агента, время последней проверки и последнюю безопасную ошибку. Действия: подключить, проверить, включить/выключить агента, отключить и переподключить.

Кнопки блокируются на время действия. Ошибки backend показываются явно; нажатие без успеха не меняет карточку на «Подключено». Различать отсутствие настройки, отсутствие внешних прав и временную недоступность сервиса.

После перезагрузки страницы и рестарта backend настройки сохраняются. Разделы используют один серверный источник состояния. Для live-режима убрать обещание, что настройки остаются только в памяти вкладки, и локальный `mailto` вместо подключения.

### 9.3. Раздел «Диалоги»

- Загружать реальные диалоги текущего бизнеса. В пустой базе показывать пустое состояние, а не примеры из `initialConversations`.
- Список: клиент/доступное имя, канал, последнее сообщение, серверное время, режим, непрочитанное состояние. Не выдумывать имя, телефон и язык, если данных нет.
- Поиск по доступным полям и тексту, фильтры по каналу и режиму — на сервере; пагинация не должна ограничивать поиск только загруженной страницей.
- Детали: сообщения клиента, агента и менеджера, события передачи, карточка и резюме из backend. Текст клиента не переводится автоматически при смене RU/EN.
- История имеет пагинацию и стабильный порядок. Время хранить в UTC, отображать в `Asia/Bishkek` для этого стенда; не заменять фактические timestamps статичными строками демо.
- Состояние прочтения хранить на сервере для оператора. Чтение в кабинете не заявлять как read receipt внешнего канала.
- У каждого диалога отдельный черновик. Ошибка отправки его не удаляет; после успешного принятия сервером текст связывается с одной исходящей операцией.
- Показывать `queued/sending/sent/failed/unknown/cancelled` в понятных формулировках. Не изображать сообщение успешно отправленным по одному оптимистичному обновлению UI.

Для первой версии достаточно polling активного списка/диалога каждые 3–5 секунд. Не создавать параллельные запросы, останавливать polling скрытой вкладки, использовать backoff при сбое и возобновлять загрузку при возвращении. SSE допустим, если оправдан, WebSocket не обязателен.

Обязательные состояния UI: загрузка, пустой список, недоступность API, отсутствие доступа, ошибка внешнего канала, отправка и повторная проверка. Сбой API не подменять демо-данными. Если сохраняется отдельный demo-режим, явно обозначить его и исключить смешивание с реальными данными.

Новые и изменяемые компоненты: Tailwind CSS, токены `plumo-blue`, `plumo-ink`, `plumo-muted`, `plumo-line`, `plumo-soft`; Hugeicons Stroke Rounded через `plumo-icon.tsx`. Сохранить адаптивность, RU/EN, клавиатурный доступ, доступные имена кнопок и существующий CSS. Изменения документов должны соответствовать фактическому состоянию функций.

## 10. Передача менеджеру и отправка ответа

### 10.1. Взять диалог

«Взять диалог» работает и для существующего handoff, и когда агент ещё не запросил помощь. Backend создаёт/принимает нужное состояние атомарно и идемпотентно, записывает событие и версию режима. Повторный клик не создаёт несколько активных передач.

После подтверждённого взятия:

- Кабинет показывает «Менеджер» и разрешает ввод.
- Новые обращения сохраняются и появляются в истории, но агент не отвечает.
- Очередь исходящих ответов агента проверяется, устаревшие отправки отменяются.
- Для стенда `MANAGER_PAUSE_HOURS=0`: агент не возвращается автоматически через текущие 24 часа.

Требуется тест гонки: клиент пишет → модель ещё отвечает → менеджер забирает диалог → результат модели не отправляется. Использовать общий механизм синхронизации перехода режима и начала отправки. После успешного accept новая отправка агента не может стартовать. Уже начатую внешнюю доставку отменить обычно нельзя; этот предел отразить в документе и сценарии проверки.

### 10.2. Ответ менеджера

Одна команда из кабинета создаёт одну серверную исходящую операцию и отправляет текст через нужное подключение. Браузер не вызывает Telegram/Meta напрямую и не выполняет две несогласованные операции «отправить» и «записать историю».

Сервер проверяет доступ, режим `human`, принадлежность диалога, подключение, текст, ограничения длины/окна канала и client idempotency key. Повтор запроса из-за двойного клика или сетевого сбоя возвращает ту же операцию. При возврате агенту до фактической отправки устаревшая команда отменяется или отвергается.

Текст виден в истории как реплика менеджера со статусом отправки. Неуспешная/неоднозначная отправка не должна попадать в контекст модели как успешно доставленная клиенту реплика. Привязку записи истории и доставки описать в контракте.

### 10.3. Вернуть агенту

«Вернуть агенту» закрывает активную передачу, меняет серверный режим и запрещает новые ответы менеджера в этом режиме. Следующее входящее сообщение обрабатывается агентом с актуальным контекстом доставленных реплик менеджера. Накопленные за паузу сообщения автоматически не вызывают очередь старых ответов после возврата.

Если `agent_enabled=false`, закрытие передачи не включает агента глобально: кабинет показывает «Автоответы выключены». Отсутствие handoff и выключенный агент — разные состояния.

## 11. Контракт API

До реализации UI согласовать и зафиксировать контракт. Пути ниже предложены для задачи и пока не существуют, если отдельно не помечено обратное. Можно изменить имена при сохранении требований и обновлении OpenAPI.

| Метод и путь | Назначение / существенные требования |
|---|---|
| `GET /api/v1/integrations` | Подключения разрешённого бизнеса, безопасная metadata и состояние агента |
| `POST /api/v1/integrations/telegram/connect` | Подключение разрешённого серверного credential, проверка бота и настройка webhook |
| `POST /api/v1/integrations/instagram/connect` | Подготовленный серверный credential; либо OAuth start/callback отдельными маршрутами |
| `POST /api/v1/integrations/{id}/check` | Повторная проверка с безопасными диагностическими данными |
| `PATCH /api/v1/integrations/{id}` | Изменение `agent_enabled`, с проверкой разрешений и версии |
| `POST /api/v1/integrations/{id}/disconnect` | Остановка отправок и корректное отключение внешней подписки |
| `GET /api/v1/conversations` | Список: курсор/limit, канал, режим, поиск, стабильная сортировка |
| `GET /api/v1/conversations/{id}` | Существующий маршрут; добавить scope, необходимые поля состояния и пагинацию сообщений |
| `GET /api/v1/customers/{id}` и `/history` | Существующие маршруты; проверить scope и безопасный контекст |
| `POST /api/v1/conversations/{id}/takeover` | Взять любой доступный диалог, без требования заранее знать handoff ID |
| `POST /api/v1/conversations/{id}/resume` | Закрыть передачу и вернуть право ответа агенту |
| `POST /api/v1/conversations/{id}/messages` | Существующий маршрут; расширить до надёжной исходящей операции менеджера |
| `POST /api/v1/conversations/{id}/read` | Продвижение read cursor оператора, без ложного unread при запоздалом запросе |
| `GET /api/v1/outbound-messages/{id}` | Проверка отправки; допустимо возвращать эти статусы в деталях диалога вместо отдельного маршрута |
| `POST /api/v1/webhooks/telegram/{connection_id}` | Секрет webhook, приём и надёжное сохранение события |
| `GET/POST /api/v1/webhooks/instagram` | Верификация callback и подписанные события Meta с маршрутизацией по получателю |

Webhook имеют собственную проверку провайдера и не требуют браузерной сессии. Сделать точечное исключение из общей авторизации; не отключать её для всего `/api/v1`. Встроенный mock endpoint `/channels/{channel}/events` не должен быть доступным обходом проверки внешнего провайдера на рабочем стенде.

Поля списка/деталей диалога: `id`, бизнес/подключение в допустимом представлении, канал, клиент, режим, версия режима, активный handoff, timestamps, preview, unread и cursor. Сообщения: ID, роль, текст, время, источник и допустимый статус отправки. Связи возвращаются только внутри разрешённого бизнеса.

Единый формат ошибок с безопасными `code`, `message`, `correlation_id`. Различать ошибки аутентификации/доступа, неизвестный объект, конфликт режима, невалидный текст, ограничение канала и временную недоступность. Серверная ошибка не возвращает токен, полный webhook или traceback в браузер.

Обновить `backend/docs/openapi.json` и frontend-типы; отдельный HTTP-клиент хранить в `frontend/src/lib` либо согласованном API-модуле. Не размазывать URL и обработку ошибок по JSX.

## 13. Проверки и критерии приёмки

### 13.1. Режимы стенда

Для разработки и воспроизводимой приёмки допустим `AI_MODE=mock`, но Telegram и Instagram должны быть реальными: клиент пишет в настоящий канал и получает сообщение от адаптера Plumo. UI обозначает mock-модель. Локальный симулятор канала не подтверждает готовность интеграции.

Если есть согласованные ключи и бюджет, дополнительно показать тот же сценарий с уже существующим production-провайдером. Выбор/обучение новой модели в задачу не входит. В отчёте явно разделить проверку транспорта, работу ядра в mock и проверку живой модели; не выдавать mock-ответ за ответ подключённой LLM.

Для приёмки использовать только разрешённые тестовые аккаунты, вымышленные данные бизнеса и сообщения без реальных данных покупателей.

### 13.2. Матрица обязательных проверок

| № | Сценарий | Ожидаемый результат |
|---|---|---|
| 1 | Подключение корректного Telegram-бота | Проверены bot ID и webhook; настройки сохраняются, агент изначально выключен |
| 2 | Неверный Telegram credential | Понятная ошибка, токен не раскрывается, `connected` не появляется |
| 3 | Подключение допустимого Instagram-аккаунта | Показаны аккаунт, подтверждённые права, настройка приёма и ограничения тестового режима |
| 4 | Неверный/отозванный Instagram credential или недостаток прав | `action_required`, отправка блокируется, доступны инструкции восстановления |
| 5 | Клиент пишет в Telegram и отдельно в Direct | В каждом канале свой реальный диалог; текст и канал корректны, агент отвечает в исходный канал после включения |
| 6 | Клиент пишет по-русски и короткий текст с кыргызскими символами | UTF-8 проходит без искажений; это проверка транспорта, не доказательство качества кыргызского агента |

### 13.3. Ручная демонстрация

Перед сдачей выполнить один и тот же сценарий отдельно в Telegram и Instagram:

1. Войти оператором, открыть «Интеграции», показать реально подключённый канал и включённый агент.
2. С тестового клиентского аккаунта отправить вопрос по вымышленной базе знаний.
3. Показать сообщение, ответ агента и карточку в кабинете, затем тот же ответ в клиентском канале.
4. Нажать «Взять диалог», отправить новое клиентское сообщение и показать, что агент молчит.
5. Написать менеджером из кабинета и показать получение сообщения клиентом.
6. Нажать «Вернуть агенту», отправить следующий вопрос и показать возобновление ответа.
7. Обновить страницу и перезапустить backend; показать сохранённую историю и режим.
8. Выключить автоответы и проверить, что новые обращения продолжают поступать.

Для стабильного локального стенда при доступных сервисах новое сохранённое сообщение должно появляться в открытом кабинете не позднее следующего успешного цикла polling плюс время запроса — ориентир 5 секунд после commit. Замерить отдельно приём webhook, обработку модели, отправку и обновление UI. Не устанавливать обещание клиентского SLA на основе mock-модели.

### 13.4. Когда работа считается выполненной

- [ ] PR создан из feature с базой `develop`, рабочая база синхронизирована.
- [ ] Кабинет закрыт авторизацией; все затронутые чтения и действия изолированы по бизнесу.
- [ ] Telegram и Instagram показаны на реальных тестовых аккаунтах, включая входящее сообщение и отправку агента/менеджера.
- [ ] UI получает историю и интеграции с backend, без неявных локальных демо-данных.
- [ ] Взятие/возврат диалога и выключение агента влияют на реальную отправку, включая конкурентные сценарии.
- [ ] PostgreSQL сохраняет состояние; входящие и исходящие задания переживают рестарт.
- [ ] Успешные, неуспешные и неоднозначные отправки различаются; повтор не создаёт вторую операцию.
- [ ] Пройдены существенные автоматические проверки из матрицы и ручная демонстрация обоих каналов.
- [ ] Обновлены инструкции, OpenAPI и `.env.example` без секретов; перечислены внешние ограничения.
- [ ] Команда может воспроизвести запуск и сценарий по документу исполнителя.

Если живой Instagram заблокирован внешними доступами, отметить отдельно завершённые пункты и оставшийся блокер. Не ставить галочку полного выполнения и не писать «Instagram работает» по одним fixtures.

## 14. Что передать вместе с PR

1. Описание проблемы и итогового поведения, список изменённых областей и миграций.
2. Инструкцию запуска из правильных каталогов: frontend, API, PostgreSQL, worker и публичный HTTPS callback. Указать реальные команды, порты, остановку процессов и порядок восстановления; не предполагать, что текущий `dev.cmd up` запускает новый worker без доработки.
3. Таблицу новых переменных окружения в `.env.example`: назначение, обязательность, пример без реальных токенов. Credential канала не должен попадать в `NEXT_PUBLIC_*`.
4. Инструкцию создания/подготовки Telegram-бота и Meta app, настройки тестового аккаунта, webhook/подписок, замены токенов и отключения. Фактические permissions, версия API и ограничения должны соответствовать выбранному варианту.
5. Обновлённые `README.md`, `frontend/README.md`, `backend/README.md`/`FULLSTACK.md` в затронутых частях и OpenAPI.
6. Результаты команд: frontend typecheck/build, существующие и добавленные frontend-тесты, backend unit/integration-тесты и lint. Записать фактические pass/fail, условия и причины пропусков; не копировать старые числа тестов из документации.
7. Заполненную матрицу приёмки: проверено автоматически, проверено вручную, не проверено и почему. Для live-тестов — канал, тип тестового аккаунта, режим модели и наблюдаемые задержки.
8. Короткую запись экрана или обезличенные скриншоты полного сценария обоих каналов. Секреты и реальные личные данные в запись и репозиторий не включать.
9. Список остаточных рисков: ограничения Meta, неопределённость внешней доставки, политика повторов и восстановления, качество кыргызского, готовность к реальному пилоту.

Сдаём работающий путь от клиентского сообщения до ответа и передачи человеку, а не только две карточки «Подключено». Контрактные тесты и красивые состояния нужны, но живую проверку каналов они не заменяют.
