# DB-09: канбан диалогов

Реализовано 2 ноября 2026. В разделе диалогов доступны List и Kanban; предпочтение хранится локально без клиентских данных. Прямая ссылка на диалог открывает List. Карточка канбана открывает существующий рабочий диалог. Старый List сохраняет свой редактор в памяти при переключении вида.

## Стадии и гарантии

Фиксированные стадии: unassigned («Без стадии»), new («Новый»), discovery («Выяснение потребности»), qualified («Квалифицирован»), meeting_requested («Запрошена встреча»), meeting_confirmed («Встреча подтверждена»).

Миграция 014 добавляет conversations.pipeline_stage (по умолчанию unassigned для новых и прежних записей), stage_version, stage_updated_at и stage_updated_by. Значения и неотрицательная версия ограничены constraints; есть индекс business_id/pipeline_stage. Стадия независима от mode/mode_version и доставки; не создаёт встречи, задания или ответы. Последний оператор и время изменения сохраняются; полного журнала стадий пока нет.

Meeting requested обозначает пожелание клиента. Meeting confirmed устанавливается только после явного подтверждения оператором (`confirm_meeting=true`), интерфейс спрашивает о согласованных дате и времени. Это ручная отметка, не интеграция с календарём, не подтверждённое бронирование и не утверждение, что слот проверен сервером.

## API

- GET `/dashboard/kanban`: stage (обязательно), q, channel, mode, cursor, limit (по умолчанию 30, максимум 100). Возвращает колонку, полный total всех подходящих карточек до применения курсора, текущую страницу и next_cursor. Поиск имени/контакта/текста сообщений и фильтры выполняются на сервере по своему бизнесу. Спецсимволы поиска экранируются; RU/KY-регистр учитывается независимо от C-locale.
- PATCH `/conversations/{id}/stage`: stage, version и необязательное confirm_meeting. Строка блокируется, бизнес проверяется через сессию и связь клиента. Старая версия — 409, чужой ID — 404, произвольные поля — 422. Повтор той же стадии с актуальной версией не увеличивает версию; конфликт не перезаписывает более новое решение.

Карточки отсортированы по последней активности и ID. Счётчик и страница одной колонки читаются одним SQL statement. Колонки загружаются параллельно и не представляют общий транзакционный снимок всей доски; живые сообщения/переносы могут менять порядок между запросами. Polling перепроверяет данные каждые 10 секунд видимой страницы. Раскрытые страницы перечитываются через курсоры, в том числе после 100 карточек.

## Интерфейс

Перенос доступен через drag-and-drop и нативный select для клавиатуры/сенсорных экранов. Интерфейс предварительно перемещает карточку и меняет счётчики. Ошибка или неизвестный HTTP-результат откатывает предварительный снимок и запускает повторное чтение; повторный PATCH вслепую не выполняется. Версия на сервере предотвращает перезапись после потери ответа. Поколение запросов не даёт poll, начатому до переноса, заменить новый снимок. При изменении фильтра данные прежнего ключа скрываются.

## Выпуск и откат

Перед новым backend применить `alembic upgrade head` с PYTHONPATH=src из выбранного checkout и явной DATABASE_URL. Экспорт контракта также запускать из него: `PYTHONPATH=src python -m app.export_openapi`; установленный editable package может указывать на исходный репозиторий.

На отдельной пустой базе проверены 001→014 и 014→013→014. Локальная база превью обновлена до 014. Production не изменялся. Downgrade удаляет стадии, версию и сведения о последнем операторе: для наполненной базы это потеря данных, не безопасный откат приложения. При откате кода предпочтительно сохранить дополнительные колонки и выключить интерфейс канбана.

Тесты покрывают полные счётчики/курсор, фильтры/поиск, две компании, конфликты и конкурентные переносы, независимость режима и очереди, подтверждение встречи без создания бронирования, optimistic rollback и страницы >100. Автоматические результаты — в PLUMO_DASHBOARD_PROGRESS.md рабочей папки. Ручная drag-and-drop, визуальная и мобильная приёмка пока не подтверждены.
