# Сквозной сценарий пилота

Основной путь: регистрация → подтверждение почты → настройка и публикация материалов → подключение Telegram-бота → ответ агента → передача и уведомление менеджеру → «Взять диалог» → ответ менеджера в канал → «Вернуть агенту» → сброс пароля. Всё это для двух бизнесов, которые не видят друг друга.

## Автоматически (CI: `.github/workflows/ci.yml`)

Каждый push и PR: линт, миграции на пустой БД вверх и вниз, все backend-тесты на PostgreSQL, frontend typecheck, тесты и сборка. Telegram, Meta и почта подменены на уровне HTTP, остальное настоящее: API, worker, очередь, БД.

## Руками на стенде (нужен постоянный HTTPS-адрес)

Не автоматизировано: настоящий браузер (Playwright не подключён, это новая зависимость), настоящие Telegram и почта.

1. Два новых пользователя регистрируются, получают письма, подтверждают почту.
2. Каждый проходит мастер, публикует материалы, подключает своего бота по токену, проходит проверочную ссылку, включает агента.
3. Каждый привязывает своего менеджера («Интеграции» → «Уведомления менеджеру»).
4. С чужого Telegram написать каждому боту вопрос о цене, затем «позовите менеджера».
5. Проверить: каждый менеджер получил только своё уведомление; ссылка открыла нужный диалог после входа.
6. Взять диалог, ответить, вернуть агенту, написать ещё раз — агент отвечает.
7. Сброс пароля одного пользователя: старая сессия закрыта.
8. Остановить worker, написать боту, запустить worker: ответ и уведомление пришли, ничего не потеряно.

Найденные блокеры записывать отдельными задачами с тестом на каждый.

## Протокол PJ-04

Заполняется на опубликованном staging для двух новых независимых пользователей. Проверки почты и Telegram на HTTP-заглушках сюда не засчитываются.
