# Кабинет, Telegram и Instagram: запуск, настройка, проверка

Инструкция исполнителя к [ТЗ](dashboard-channel-integration-spec.md). Ветка `feature/dashboard-telegram-instagram`, база — `develop`. Состояние на 15 октября 2026.

## 1. Что сделано и что нет

| Часть | Состояние |
|---|---|
| Закрытый вход в кабинет | Сделано. Операторы создаются на сервере, сессия в HttpOnly cookie, публичной регистрации нет |
| Изоляция по бизнесу | Сделано. Все маршруты кабинета, включая старые (`/customers`, `/handoffs`, `/knowledge`, `/metrics`), берут бизнес из сессии |
| «Интеграции» и «Диалоги» на данных backend | Сделано. Демо-массивы удалены; опрос сервера каждые 3–4 с |
| Надёжный приём webhook, worker, доставка | Сделано, покрыто тестами. События и задания в PostgreSQL, повторы, lease, `unknown` |
| Telegram-бот | Сделано и проверено вживую на тестовом боте @plumoAiBot (раздел 10): подключение, приём, ответ модели, взять диалог, ответ менеджера, вернуть агенту, отключение и повторное подключение. Стенд временный: быстрый туннель cloudflared |
| Instagram Direct | Код готов, проверен на подписанных fixtures. **Живая проверка невозможна**: у команды нет Meta app и доступов. В кабинете канал показан как «Требуется действие» |
| WhatsApp | Без изменений: демонстрационный мастер |

Полная задача по Instagram остаётся невыполненной до живой проверки входящего Direct и ответа (ТЗ §7.4).

## 2. Как это устроено

```text
Telegram / Meta webhook → FastAPI /api/v1/webhooks/*
  → проверка подлинности (secret_token / X-Hub-Signature-256 по сырому телу)
  → подключение и business_id из нашей таблицы, не из payload
  → одна транзакция: inbound_events + jobs → commit → HTTP 200
worker (python -m app.worker)
  → забирает задание (SKIP LOCKED, lease 120 с), по одному на клиента
  → AgentService (существующее ядро) → история, действия, ответ
  → в той же транзакции: outbound_messages + задание отправки
  → отправка: под блокировкой диалога заново проверяет подключение,
    agent_enabled, режим и его версию, окно Instagram → sending → провайдер
  → sent (провайдер принял) / повтор / failed / unknown

Браузер → Next.js (/api/auth/*, /api/plumo/* — белый список) → FastAPI
  (X-API-Key сервера Next.js + Bearer-сессия оператора)
```

Новые таблицы (миграция `006_channels_dashboard`): `operators`, `operator_sessions`, `channel_connections`, `inbound_events`, `jobs`, `outbound_messages`, `conversation_reads`. В `conversations` добавлены `business_id`, `connection_id`, `mode`, `mode_version`, `mode_changed_at`, `external_chat_id`, `contact_name`, `contact_handle`. В `messages` добавлен `seq`: порядок вставки и курсор прочтения. Существующие диалоги получают `business_id` клиента. Диалоги с принятым handoff переходят в режим `human`. Связи с подключением у старых диалогов нет: читать их можно, отвечать из кабинета нельзя.

Клиент канала привязан к аккаунту бота: в `customer_channels.external_id` хранится `<id бота или IG-аккаунта>:<id клиента>`. При замене бота или Instagram-аккаунта прежняя история не открывается новому собеседнику с тем же id. Повторное подключение того же аккаунта возвращает ту же запись подключения и ту же историю.

## 3. Запуск на Windows

Все команды backend — из папки `backend`, frontend — из `frontend`.

```powershell
# backend, первый раз
.\dev.cmd setup
.\dev.cmd db                 # локальный PostgreSQL на :5432
.\dev.cmd seed               # миграции + Demo Realty
.\dev.cmd operator create --email you@example.kg --business "Demo Realty" --name "Имя"
#   пароль спросит интерактивно (не меньше 10 символов)

# каждый день — три окна
.\dev.cmd run                # API http://127.0.0.1:8000 (Swagger /docs)
.\dev.cmd worker             # worker: обработка входящих и отправка ответов
cd ..\frontend; npm run dev  # кабинет http://localhost:3000/dashboard
```

`frontend/.env.local` (по образцу `frontend/.env.example`):

```
PLUMO_API_URL=http://127.0.0.1:8000
PLUMO_API_KEY=<то же значение, что в backend/.env>
```

`dev.cmd up` новый worker не запускает: его нужно держать в отдельном окне. Остановка — Ctrl+C в каждом окне, база — `.\dev.cmd db-stop`. После перезапуска worker сам продолжает незавершённые задания. Задание упавшего процесса снова берётся после истечения lease (120 с).

### Публичный HTTPS для webhook

Telegram и Meta ходят только на публичный HTTPS-адрес. Наружу нужен только API (порт 8000). Кабинет может оставаться локальным.

```powershell
cloudflared tunnel --url http://127.0.0.1:8000
# → https://<случайное-имя>.trycloudflare.com
```

Адрес записать в `backend/.env` как `PUBLIC_BASE_URL`, перезапустить API и worker. Быстрый туннель меняет адрес при каждом запуске. После смены адреса Telegram надо подключить заново: кабинет покажет конфликт webhook со старым адресом и кнопку «Заменить webhook». Для постоянного стенда нужен именованный туннель или сервер с доменом.

На публичном адресе API обязательно задать `PLUMO_API_KEY` и `APP_ENV=stand`. Без `PLUMO_API_KEY` и `CHANNEL_SECRET_KEY` API в режиме stand не запустится, а mock-маршрут `/channels/{channel}/events` в нём выключен.

## 4. Telegram: подготовка и подключение

1. В Telegram открыть @BotFather → `/newbot` → имя и username бота (оканчивается на `bot`). BotFather выдаст токен вида `123456789:AA...`.
2. В `backend/.env`:
   ```
   TELEGRAM_DEMO_BOT_TOKEN=<токен>
   CHANNEL_SECRET_KEY=<длинная случайная строка>
   CHANNEL_CREDENTIALS_FILE=channel-credentials.json
   PUBLIC_BASE_URL=https://<адрес туннеля>
   MANAGER_PAUSE_HOURS=0
   ```
3. Скопировать `backend/channel-credentials.example.json` в `backend/channel-credentials.json` (файл в `.gitignore`) и вписать id бизнеса. Id печатает `.\dev.cmd seed`; у Demo Realty он `11111111-1111-4111-8111-111111111111`.
4. Перезапустить API и worker. В кабинете: «Интеграции» → Telegram → «Подключить». Выбрать «Тестовый бот Plumo» и нажать «Проверить и подключить». Backend вызывает `getMe`, `getWebhookInfo` (чужой webhook молча не перезаписывается) и `setWebhook` с отдельным `secret_token`. Ответы агента после подключения выключены.
5. С другого аккаунта написать боту и убедиться, что обращение появилось в «Диалогах».
6. Включить агента кнопкой на карточке. Переключатель сохраняется на сервере.

Токен и `secret_token` не хранятся в БД и не попадают в браузер. Secret выводится из `CHANNEL_SECRET_KEY` и случайного nonce подключения. В логах токен из URL Telegram вырезается, логи httpx приглушены.

Замена токена: в @BotFather `/revoke`, новый токен записать в `.env`, перезапустить API и worker, на карточке нажать «Проверить». Если бот другой, сначала «Отключить», потом подключить заново. Отключение удаляет только наш webhook (`deleteWebhook` без сброса очереди Telegram) и отменяет неотправленные ответы. История сохраняется.

Бот уведомлений менеджеру (`HANDOFF_PROVIDER=telegram`, `TELEGRAM_BOT_TOKEN`) — отдельная настройка. Один токен для обеих ролей не использовать: клиентский бот работает через webhook, и `getUpdates` для него недоступен.

## 5. Instagram: что нужно от владельца Meta-аккаунта

Выбран путь **Instagram API with Instagram Login**: профессиональный аккаунт Business или Creator, связанная Facebook Page не нужна. Сверено с документацией Meta 14 октября 2026; в примерах API v25.0, версия задаётся в `INSTAGRAM_API_VERSION`.

Нужно (сейчас у команды этого нет):

1. Профессиональный аккаунт Instagram (Business или Creator) для теста и второй аккаунт, с которого пишет «клиент».
2. Meta app типа Business. В нём продукт Instagram, раздел «API setup with Instagram business login».
3. Разрешения `instagram_business_basic` и `instagram_business_manage_messages`. Тестеры приложения и тестовый аккаунт должны иметь роли в приложении. Для чужих аккаунтов нужен Advanced Access через App Review.
4. Приложение в режиме **Live**: без него Meta не отправляет webhook.
5. Токен: «Generate token» рядом с аккаунтом. Токен из App Dashboard живёт 60 дней.
6. Webhooks: Callback URL `https://<PUBLIC_BASE_URL>/api/v1/webhooks/instagram` (кабинет показывает его в панели подключения), Verify token — значение `INSTAGRAM_VERIFY_TOKEN`, подписка на поле `messages`.

В `backend/.env`:

```
INSTAGRAM_DEMO_ACCESS_TOKEN=<токен>
INSTAGRAM_APP_SECRET=<Instagram app secret со страницы API setup>
INSTAGRAM_VERIFY_TOKEN=<придумать и вписать в Meta>
```

Затем в кабинете: «Интеграции» → Instagram → «Проверить и подключить». Backend проверяет аккаунт (`GET /me`) и подписку (`POST /me/subscribed_apps?subscribed_fields=messages`).

Правила, заложенные в код:

- Дедупликация по `mid` сообщения. Echo собственных ответов, прочтения, реакции, правки и удаления агента не запускают.
- Вложения и `is_unsupported` сохраняются как неподдерживаемые. Клиент один раз получает ответ «пишите текстом».
- Ответ возможен только в течение **24 часов** после последнего сообщения клиента. Вне окна отправка блокируется и для агента, и для менеджера. Тег human agent не используется.
- Текст не длиннее 1000 байт. Длинный ответ агента уходит частями, ответ менеджера проверяется на лимит.
- Ошибка токена (код 190) или прав (10, 200–299) переводит подключение в «Требуется действие». Отправки останавливаются.
- Обновление токена не автоматизировано: заменить его до истечения 60 дней. Endpoint `refresh_access_token` перед использованием сверить с документацией Meta.

Ошибки Meta и подкоды окна (2534022, 2018278) взяты из общих правил Graph API. Их нужно подтвердить на живом приложении.

| `CHANNEL_SECRET_KEY` | ключ, из которого выводятся секреты Telegram-webhook | для Telegram да |

| `MANAGER_PAUSE_HOURS` | для стенда `0`: агент не возвращается сам | рекомендовано |
| `INBOUND_RETENTION_DAYS` | через сколько дней у обработанных webhook-событий стираются текст и имя (история диалога остаётся); `0` — хранить всегда, по умолчанию 30 | нет |

## 7. Надёжность: политика и пределы гарантий

| Ситуация | Поведение |
|---|---|
| Повтор webhook | Уникальность `(connection_id, external_event_id)`: Telegram — `update_id`, Instagram — `mid`. Повтор не создаёт сообщение, задание, вызов модели или отправку |
| Отказ БД при приёме | Ошибка без 2xx, провайдер повторит. Ответ 2xx только после commit |
| Порядок | Задания с одним ключом (`in:<подключение>:<клиент>`, `out:<диалог>`) выполняются по одному в порядке создания. Разные клиенты — параллельно |
| Падение worker | Lease 120 с. Обработка входящего — одна транзакция: незакоммиченное повторяется. Не больше 5 попыток (5, 10, 20… с, максимум 120), затем `failed` |
| 429 | Повтор через `retry_after` Telegram или 60 с для Meta |
| Временный сбой до отправки | Повторы 2, 4, 8… с (максимум 60), всего 4 попытки, затем `failed (retries_exhausted)` |
| Таймаут после отправки, 5xx при отправке | `unknown`, автоматического повтора нет. Менеджер решает в кабинете: «Клиент получил», «Не дошло», «Отправить ещё раз» (последнее только для своих сообщений) |
| Worker упал во время `sending` | При следующем захвате — `unknown (interrupted)` |
| Недействительный токен, нет прав | `failed`, подключение — `action_required`, без бесконечных повторов |
| «Взять диалог» | Атомарно и идемпотентно: принимает ожидающую передачу или создаёт новую. Режим `human`, версия +1. Очередь ответов агента отменяется. Повторный клик ничего не дублирует |
| Модель ещё генерирует, менеджер взял диалог | Ответ сохраняется, но с прежней версией режима. Перед отправкой это видно, ответ отменяется (`cancelled, mode_changed`) |
| «Вернуть агенту» | Передачи закрываются, режим `ai`, версия +1. Неотправленные сообщения менеджера отменяются |
| Выключенный агент | Сообщения принимаются и видны, автоответов нет. Менеджер может взять диалог и ответить |
| Отключение канала | Webhook снят (только наш), секрет аннулирован, очередь отправок отменена, история сохранена. При повторном подключении старые ответы не уходят, агент выключен |

`sent` означает, что провайдер принял сообщение и вернул его id. Это не прочтение клиентом. Прочтение в кабинете — отметка оператора, а не read receipt канала.

Пределы:

- Уже переданную провайдеру отправку отменить нельзя. Если менеджер взял диалог в момент отправки, ответ агента может дойти.
- Exactly-once не гарантируется: у Telegram и Meta нет ключа идемпотентности, поэтому неоднозначный результат становится `unknown`, а не повторяется.
- Платный вызов модели может завершиться до падения процесса и commit. Тогда событие обработается повторно и модель будет вызвана ещё раз. Дедупликация событий не защищает от двойного биллинга при любом падении.
- Лимит попыток входа хранится в памяти процесса API (8 неудач за 15 минут на email). При нескольких процессах API лимит считается отдельно.

## 8. Безопасность

- Страница `/dashboard` проверяет сессию через backend на сервере. API кабинета требует `X-API-Key` сервера Next.js и Bearer-сессию. Без них ответ 401.
- Прокси Next.js пропускает только перечисленные маршруты (`frontend/src/lib/api/routes.ts`) и параметры запроса.
- Изменяющие запросы требуют Origin своего сайта и заголовок `x-plumo-request`. Cookie: HttpOnly, SameSite=Lax, Secure на HTTPS (в том числе за туннелем). Срок — `SESSION_TTL_HOURS`, выход отзывает сессию на сервере.
- Чужой `business_id` или id объекта другого бизнеса даёт 404 на всех маршрутах кабинета: тест `test_25_26_other_business_and_anonymous_calls_are_refused`.
- Секреты не возвращаются в API, не попадают в браузер (проверено поиском по клиентскому бандлу) и не пишутся в логи.
- Ошибки отдаются в формате `{error, code, message, correlation_id}`. Traceback, токены и webhook клиенту не уходят.
- Сохраняется только нужное для обработки: текст, id отправителя и чата, имя и username из Telegram. У проигнорированных событий хранится только тип. Через `INBOUND_RETENTION_DAYS` (30 дней) worker стирает текст и контактные данные из обработанных событий; переписка в диалогах остаётся, её срок хранения и удаление нужно согласовать до работы с реальными покупателями.

## 9. Контракт API (новое и изменённое)

Полная схема — `backend/docs/openapi.json`.

| Метод и путь | Назначение |
|---|---|
| `POST /api/v1/auth/login` · `POST /auth/logout` · `GET /auth/me` | вход оператора, только для сервера Next.js |
| `GET /api/v1/integrations` | каналы бизнеса, доступные конфигурации, готовность сервера |
| `POST /api/v1/integrations/{telegram\|instagram}/connect` | проверка и подключение (`credential_ref`, `replace_webhook`) |
| `POST /api/v1/integrations/{id}/check` · `PATCH /{id}` · `POST /{id}/disconnect` | проверка, агент вкл/выкл (с `version`), отключение |
| `GET /api/v1/conversations` | список: `channel`, `mode` (`ai`/`waiting`/`human`), `q`, `cursor`, `limit` |
| `GET /api/v1/conversations/{id}` · `GET /{id}/messages?before=` | детали: сообщения со статусами доставки, клиент, резюме, передача, `reply` (можно ли отвечать и почему) |
| `POST /api/v1/conversations/{id}/takeover` · `/resume` | взять диалог и вернуть агенту |
| `POST /api/v1/conversations/{id}/messages` | ответ менеджера: `text`, `idempotency_key`. Повтор с тем же ключом возвращает ту же операцию |
| `POST /api/v1/conversations/{id}/read` | курсор прочтения, двигается только вперёд |
| `GET /api/v1/outbound-messages/{id}` · `POST /{id}/resolve` | статус отправки и ручное решение по `failed`/`unknown` |
| `POST /api/v1/webhooks/telegram/{connection_id}` · `GET/POST /api/v1/webhooks/instagram` | вход провайдеров со своей проверкой подлинности |

Изменено: маршруты карточки, истории, handoff, базы знаний и метрик требуют сессию оператора и ограничены его бизнесом. Старый `POST /conversations/{id}/messages`, который только записывал текст, заменён надёжной отправкой: в диалоге без подключённого канала он отвечает `422 channel_not_connected`. `/channels/{channel}/events` работает только при `APP_ENV=development`.

## 12. Остаточные риски

- **Instagram не проверен вживую.** Нужны Meta app, роли, режим Live и при необходимости App Review. Подкоды ошибок и окно ответа подтвердить на живом приложении.
- **Telegram работает на временном адресе.** Быстрый туннель меняет адрес при каждом запуске; для стенда команды нужен сервер с доменом или именованный туннель.
- Неоднозначная доставка (`unknown`) требует ручного решения; exactly-once невозможен без поддержки провайдеров.
- Повторный вызов модели и биллинг при падении worker до commit.
- Сырые события очищаются через 30 дней, но срок хранения самой переписки и порядок удаления данных клиента не определены; согласовать до реальных покупателей.
- Лимит попыток входа в памяти процесса; полноценных ролей нет, один оператор — один бизнес.
- Качество кыргызского проверяется с носителем; здесь проверен только транспорт UTF-8.
- Готовность к реальному пилоту: нужен постоянный сервер с доменом, резервное копирование БД и мониторинг worker.
